# Kime Zanshin basic preview check v1

2026-11-11。公開可能な合成課題のみ。外部操作・実機・実データは使わない。

対象: 新規skill本文とreferences、coding側の責務と任意導線。
目的: 代表的な模擬依頼で指示が実行可能かを確かめる。性能改善・独立skillの優位の評価ではない。

## 固定ケースと判定観点

1. 保存ボタン: 受付反応と保存確定を分け、遅延・失敗の間も入力を失わず、保存の保証に応じて確認する。速い表示だけを性能改善や保存成功の証明にしない。
2. 結果不明: 発行処理の応答喪失時に、実行済みかを読取照合してから判断し、無条件再送による重複を避ける。照合できなければ不明として扱う。
3. 資料引き継ぎ: draft作成・利用可・受領・理解を区別し、次の担当が必要な版・未完了を把握できる形を作る。未許可の送信、受領の断定、無期限の監視をしない。
4. 明確な誤字: 指定の修正だけを行い、計画・状態表・新たな確認待ちを増やさない。
5. 設計でpreview未導入: coding単独で設計を進め、preview導入を前提にしない。旧応答による新しい入力の上書きと、必要な状態・検証境界を扱う。
6. 実装の検証報告: 合成自動操作とread-backの証拠、物理入力・実機・利用者評価の未確認を区別する。手動連打を繰り返す代わりに、限定された再実行可能なtestを用いる。

各ケースは記載の重要観点を満たし禁止する誤りがなければ、この限定課題についてPASS。不明は未確認、失敗はFAIL。生成者には期待解を渡さず実際のpromptと対象skillだけを渡す。結果を見て同じrunの基準を変えない。原回答と対象hash、実行者・採点者、限界を残す。

## 限界と後続評価

小数の公開合成課題であり、統計的優位・自動discovery・速度・耐久性・実利用効果は未検証。A/B/C比較は別runで入力・基準・試行数を固定して実施する。この確認だけでcoreへ昇格しない。
