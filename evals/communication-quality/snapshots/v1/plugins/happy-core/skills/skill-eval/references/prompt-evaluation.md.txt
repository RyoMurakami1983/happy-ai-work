# Prompt evaluation

Criteria version: 2.0.0。旧版1.0.0は[保存版](../snapshots/prompt-evaluation.v1.md)、変更の影響と所有者承認は[移行判断](evaluation-criteria-v2.md)を参照する。過去runには遡及適用しない。

## Scenario set

- typical: 最頻の利用例
- edge: 判断境界または失敗しやすい条件
- negative: 似ているがskillを起動すべきでない依頼
- hold-out: 修正に使わず、収束時だけ使う例

各scenarioに最低一つのcritical要件を置く。評価後に要件やscenarioを簡単な方向へ変えない。

## 成果物保存ポリシーのscenario

- edge — small one-slice: 明らかに小さく低riskな単一sliceで、後続handoffや判断記録が不要。conversation-onlyを選ぶ場合、具体的な `exception reason` があること。
- critical — artifact save required: multi-repo、複数slice、public contract、long-lived structure、compatibility、migration / operationsのいずれかを含む。conversation-onlyを選ばず、canonical pathへ保存し、handoffに実在pathを列挙すること。

## 記録項目

| 項目 | 意味 |
| --- | --- |
| trigger | 起動すべき／すべきでない条件を満たしたか |
| critical | 最低条件をすべて満たしたか |
| coverage | 通常要件の達成割合 |
| ambiguity | 実行者が解釈に迷った文言 |
| discretion | 指示がなく実行者が補った判断 |
| waste | 成果に寄与しない探索や手順 |
| risk | 未検証の副作用、権限、環境差 |
| communication | 利用者が理解・判断・行動できる必要十分な伝達と、その時点 |

量的なstep数や時間は補助指標とし、品質低下と引き換えに短縮しない。

## 共通のコミュニケーション品質

全skillの評価で、最終回答だけでなく必要な途中通知も観測する。この観点を使う評価では本referenceを読む。

- 判断・行動に必要な情報が足りるか。
- 将来困る重要条件、不利益、不確かさを、判断や実行に間に合う時点で伝えたか。
- 無関係な説明、取得済み許可の再質問、読み直しや推測による補完を利用者へ強いていないか。

判定は**十分／改善余地あり／判断・行動に支障**とし、発言や通知の時点、利用者への影響を短い根拠として残す。実際の発言・順序を観測できなければ未観測と記す。文字数・見出し数や`yohaku`の呼出し自体は加点しない。学習や詳しい説明が目的なら、その目的に必要な深さを保持する。

正確さ・安全・依頼達成とdecision invariantsを満たした候補同士では、判断・行動の支障をなくす改善を優先する。同等なら不要な補完・再読・質問の負担が少ない候補を採る。「改善余地あり」は影響と保守コストを比較し、単に短い候補を優先しない。downstreamでは適用する基準・優先度を対象の方針で実行前に固定し、upstream固有の重みを暗黙適用しない。

coverageは要件の達成、wasteは探索・手順、riskは副作用・権限・環境差を扱う。communicationはresponse quality内の伝達観点である。同じ欠点は主となる一項目で評価し、他は関連として参照して重複減点しない。非安全な省略だけで全体Critical FAILにしない。安全上の欠落や最終record contract違反は既存gateに従い、重要条件の欠落をCriticalとするscenarioは実行前に固定する。

最小対照例（手数料付き予約変更の判断、まだ実行未承認）:

| 観測 | 判定 | 短い根拠 |
| --- | --- | --- |
| 「10時に変更できます。手数料は1,000円です。変更しますか？」 | 十分 | 時刻と費用を判断前に伝えた |
| 「10時に変更できます」 | 判断・行動に支障 | 費用を補完しないと判断できない |
| 時刻と費用に加え、依頼に関係ない予約システムの歴史を説明 | 改善余地あり | 判断情報はあるが探索・再読の負担が増える |
| 変更を実行してから手数料1,000円を通知 | 判断・行動に支障 | 費用を踏まえて選ぶ機会を失った。無承認実行なら安全gateでも扱う |

完了済みの依頼に追加質問を強制しない。これらは公開対照例であり、未見hold-outでも人の認知負担の計測でもない。

## 反復

1. 不明瞭点を一つの変更テーマへまとめる。
2. どの判定項目を改善する変更か先に書く。
3. 新しい独立実行で同じscenarioを再評価する。
4. 収束時にhold-outを実行する。

同じ実行者は前iterationを学習しているため、独立評価として再利用しない。独立実行が利用できない場合は、別taskでの後続評価を依頼する。
