# ADR 0012：判断軸・実務手段・試用と評価の責務を分ける

Status: Accepted decision / implementation pending
Date: 2026-11-13
Owner: RyoMurakami1983

## 背景

happy-coreには、判断軸、環境設定、課題化、改善、評価の手順が同居している。所有者は2026-11-13の対話で、coreを自身のprivate evalを支える判断軸として明示し、具体的な実務手段と分ける方針を決定した。

何を良しとするかを採用する判断と、その判断軸を用いた手段が実際に役立つかを確認する評価は異なる。採用した判断軸までpreviewの昇格待ちにすると、この区別が失われる。一方、coreにあることだけで有効性を実証したことにはならない。

現行ADR 0004は、構想、基本検証、previewでの試用、実利用確認、通常配布の流れを定めている。全変更に大規模な定量実験を必須としていたわけではない。今回の変更は評価をなくすことではなく、対象と責任を分けることである。

## 新旧の違い

| 項目 | これまで | 今回の決定 |
| --- | --- | --- |
| core | 共通作業・環境初期化・ふりかえり・改善・Issue intake・評価を包含 | 採用した判断軸を中心に構成する。導入機能は判断軸と区別する |
| 判断軸の採用 | previewの通常昇格条件と区別されず、短歌と俳句には限定承認を記録 | coreの判断軸はpreviewに入れない。具体例・反例を確認して所有者が採用する |
| 実務手段 | coreとcodingに分散 | coding、強化と改善など目的に合うpluginへ配置する |
| preview | 基本検証済みの試用skillを任意配布 | 実務手段の試用先とする。coreの判断軸は対象外 |
| 評価道具 | skill-evalをcoreで配布 | 強化と改善側に置き、分野をまたいで利用する |
| coreと実務の接続 | 各本文・referenceに分散 | 実務skillから適用するcoreを明示参照し、本文のコピーを避ける |
| 確認する証拠 | 起動・振る舞い・成果の比較手順を保有 | 実際の読込と、観察可能な過程・結果を区別して確認する |

## 決定

### 1. coreは判断軸を中心にする

coreは「何を良しとするか」「複数の妥当な選択肢のうち何を選ぶか」を表す。具体的な手順をすべて排除すること自体が目的ではないが、判断軸と実行方法を識別できるようにする。

coreの判断軸はpreviewを経由しない。案を具体例・反例に当て、判断が変わる点、曖昧さ、既存軸との重なりを確認して所有者が採用する。採用後も実務での違和感を改訂材料にする。採用は効果検証済みという意味ではない。

home-bootstrapは共通方針をhome環境へ届ける導入機能としてcoreに残す方向とする。判断軸そのものと同じ種類のものとは説明しない。

### 2. 実務手段を目的別に配置する

codingは開発・repo固有の作業を、強化と改善（仮称）は課題化・改善実験・評価などの横断的な作業を扱う。将来writingやreadingが必要になった場合も同じ責務分離を使うが、この決定で新設を実施するわけではない。

| 配置方針 | 対象 |
| --- | --- |
| core | 問いと見極め（現interview-me）、ふりかえりと想い（現furikaeri）、余白、極めと残心、短歌と俳句、home-bootstrap（改名検討） |
| 強化と改善（仮称） | improvement-loop、happy-add-issue、skill-eval |
| coding | workspace-bootstrap、github-issue |

skill-evalのアーカイブ案は採用せず、強化と改善側で評価手段として保持する。home-bootstrapをcodingへ移す先行案も採用しない。github-issueは通常の作業依頼にも使うため、改善だけに用途を狭めない。

これは移行先の方針であり、現在の配布先や名称を表す表ではない。

### 3. 実務skillからcoreを明示参照する

実務skillには、適用するcoreの判断軸への参照と、その仕事で何を判断するために使うかを示す。core本文を各skillへコピーして二重管理しない。必要な概念を一つ以上持つことを基本とし、coreの概念が一つも関わらない実務skillは通常の構成として想定しない。

これは全coreの常時読込、装飾的なリンク、無関係な軸の強制を意味しない。実務上の判断と結び付けられない場合は、参照だけを付けず、そのskillの役割・配置・境界を見直す。

参照が存在することと、実行時に読まれ適用されたことは別である。評価では利用環境、対象version、実際の読込・適用を示す証拠を残す。証拠が得られなければ未確認とし、自動起動や適用済みと推測しない。別pluginのcoreを参照するときは、その利用先で到達可能かも確認する。

### 4. previewは実務手段の試用に使う

新しい実務手段は、目的・trigger、実行可能な手順、形式・参照・安全性の基本確認を経てpreviewで試す。期待する価値、観察点、見直す条件を先に決める。

試用の結果は採用、修正して継続、保留、撤回のいずれかへ結び付ける。保留は不足する根拠や再開条件を残す。時間経過だけを採用理由にせず、際限なく評価することも目的にしない。

ADR 0004の任意導入、通常版との識別、重複配布禁止、正式化・撤回時の移行案内は維持する。今回の配置変更だけで、既存の実務skillを一律にpreviewへ戻さない。振る舞いを変える部分に応じて確認する。

### 5. 評価の道具は強化と改善に置く

skill-eval等で、対象の実務手段を関連するcoreの判断軸と仕事固有の完了条件に照らして確認する。評価する手段と、評価に使う判断軸のversionを区別して記録する。

最小限、次を残す。

- 何を確かめたかったか、どの判断軸と完了条件を使ったか。
- 実際の読込・適用の証拠と、観察可能な過程・結果。
- 分かったこと、失敗、未確認のこと。
- 採用・修正・保留・撤回の判断と理由。

過程は観察した情報、確認、選択理由、行動、修正などで確認する。文章の長さやもっともらしさを解像度の代わりにしない。内部の思考内容を取得できたと仮定しない。

確認の規模は変更の大きさ、可逆性、リスク、主張する効果に合わせる。小さな変更は代表例と回帰確認から始め、追加価値の比較を主張する場合や大きな変更では条件を揃えた独立比較を行う。静的確認を行動評価と呼ばず、差が出ないことを同等性の証明にしない。

評価対象である評価手順自体の変更も、変更済み手順だけで自己認証しない。固定した基準・証拠と独立した確認を保つ。確認を小さくしても安全・評価整合性は緩めない。

### 6. 正本・公開境界と過去履歴を維持する

CONSTITUTION.mdは引き続き公式projectの判断原則と統治境界の正本である。coreはこれを置き換える第二のConstitutionではなく、採用した判断軸を利用可能な形で表す。原則の意味・優先順位を変える場合は、現行Constitutionを維持したvNext案、影響比較、所有者の明示承認を経る。

「本人のprivate evalを支える判断軸」と、利用者管理の非公開のscenario・rubric・実行記録は区別する。公開coreを非公開評価資産全体とは呼ばない。公開可能な実評価はupstream evalまたは共通安全evalとして扱う。

公式projectでは所有者の判断軸を用いるが、配布先の所有者固有の目的・価値観へ暗黙に上書きしない。明示参照によって、downstreamの所有境界や共通安全境界を迂回しない。

過去の評価結果・基準・snapshotを新しい方針に合わせて書き換えない。再評価は別version・別recordとする。ADR 0001、0002、0006の境界を維持する。

## 既存ADRとの関係

- ADR 0004のpreview運用は実務手段を対象とする。core判断軸への適用は本ADRで置き換える。短歌と俳句の過去の限定承認を、当時の通常評価PASSへ読み替えない。
- ADR 0007の旧余白の扱いは歴史として保持する。余白を、詰め込みすぎも不足も避け、挑戦・判断・変化の余地が作品や作業にあるかを見る判断軸へ作り直す。表示名は「余白」とする。従来の文章整理手順は短歌と俳句との重複を確認して扱いを決める。
- 余白の再定義を理由に、ADR 0007で除去したhomeの開始時生成や全skillへの本文複製を復活させない。

## 影響と移行

判断軸の採用待ちと手段の検証待ちを分離し、方法を交換しても評価の観点を保ちやすくなる。一方、参照関係と配布依存の保守が増え、参照だけで適用したつもりになる危険があるため、実読込と過程・結果を確認する。

この変更ではADRだけを記録する。skill本文・配置・manifest・namespace・CI契約はまだ変更しない。後続の実装では、現在の製品説明と配布実態を保ちつつ、CONTEXT、README、参照、必須skill一覧、契約test、更新案内を同じ移行単位で整合させる。

実装前の未決事項は、強化と改善の正式名と範囲、各coreの本文と手順の境界、旧余白の文章整理手順、home-bootstrapの名称、配布先での参照・導入方法である。core判断軸の採用を待つことと、配布変更の準備が未完了なことは区別する。

## 配置方針の更新（2026-11-14）

所有者の明示決定「Github-issueはcodingに入れましょう」により、github-issueは強化と改善ではなくhappy-codingへ配置する。通常の実装backlog整理を、スキル開発者向け任意pluginの導入に依存させないためである。軽いHappy AI Work feedbackを扱うhappy-add-issueは強化と改善に残す。今回の配置変更でskill本文・手順・名前は変えない。
