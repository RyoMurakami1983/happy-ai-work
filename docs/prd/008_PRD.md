# PRD 008: 相談から成果物変更へ移る判断

## Context / Problem

Issue [#33](https://github.com/RyoMurakami1983/happy-ai-work/issues/33) と、2026-09-25のホーム・repo指示の実ファイル確認を根拠とする。利用者は、コーディング相談で最初に挙がった改善案からAIがすぐ成果物を修正することに困っている。最初の案は困りごとの説明や候補であり、採用・変更依頼とは限らない。

現行のホーム共通方針は目的把握、小さな変更、検証を定めるが、相談と変更依頼を区別する条件を明記していない。repo指示はrepo固有の境界を、`implement` skillは実装開始後の手順を扱う。Issue #17のfinalization gateは採用決定後の恒久成果物への混入を扱い、今回の着手判断とは段階が異なる。

## Purpose

利用者が相談・分析・比較を依頼したときは判断材料を得られ、成果物の変更を任せたときは不要な確認なしに修正・検証まで進む。

## In Scope

- ホーム用共通方針の配布テンプレートに、会話の段階に応じた着手判断を加える。
- 現行のhome／repo／workspace指示と実装skillの責務を照合する。
- 相談中の誤着手と、明確な変更依頼への過剰停止を両方向から確認する。

## Out of Scope

- すべての変更前に計画書や追加承認を必須にすること。
- Issue #17のfinalization gateを作り直すこと。
- repo固有の規則をホームへ移すこと、または全workspaceへ共通文言を複製すること。
- 配布テンプレートの編集を、個人ホームへ自動適用すること。

## Requirements / Acceptance Criteria

| 要件 | 必要な状態 | 受入条件 |
| --- | --- | --- |
| R-01 | 会話中の候補案・賛意・採用・変更依頼を混同しない | AC-01: 改善案の提示と分析依頼では読取調査と回答を進め、依頼されていない成果物変更を始めない。AC-02: 案への賛意と追加の比較依頼が続く場合も、賛意だけで変更を始めない。 |
| R-02 | 変更が任された後の自律性を保つ | AC-03: 明確な修正依頼では、対象範囲の修正と検証まで進み、形式的な再承認を求めない。AC-04: 実装中に目的や対象を変える未決事項が生じた場合だけ、その判断を切り出す。 |
| R-03 | 規則を適切な階層に置く | AC-05: 共通の着手判断をホーム向けテンプレートに短く置き、repo固有規則とskill手順を重複させない。既存の共通方針6項目を維持する。 |
| R-04 | 配布と個人適用を区別する | AC-06: テンプレート変更後も個人ホームは自動変更されない。個人適用時には対象と差分を示し、既存のdry-run・backup・承認条件に従う。 |

AC-01〜03は単発の文言例だけでなく、初期案から困りごとが明確になる複数ターンの例でも確認する。評価では回答内容に加え、実際のファイル書き込み有無を観測する。モデルの行動効果が未測定なら、文言の検査だけで効果を実証済みとしない。

## Fixed Constraints / Dependencies

- `README.md` はホーム共通方針を6項目として説明する。
- `home-bootstrap` は管理対象マーカー内のみを更新する。実ホームへの適用はdry-run、差分、backup、明示承認を要する。
- repoの `AGENTS.md` は恒久規約に採用済み根拠を求める。今回の根拠は本PRDのACとIssue #33。
- 2026-09-25に利用者は、dry-runで示した第一項目だけの差分を個人ホームへ適用することを明示承認した。

## Unknowns

- 正式な行動評価と採用判定は未実施。更新後の探索的な隔離試行は参考観測であり、旧版との比較や複数環境での再現性も未確認。
