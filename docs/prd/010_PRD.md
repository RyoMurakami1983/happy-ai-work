# PRD 010：判断と次の行動が分かる技術設計レビュー

2026-09-26 / v1 / Issue #35

## 文脈と問題

利用者は `technical-design-review` の回答を読んでも、「BLOCKED」「ドメインモデルへ戻す」の意味や、自分に何を判断してほしいのかが分からず、質問し直す必要があった。利用者は本会話で、主な困りごとは「説明の意味が分からなかったこと」と特定した。

求めているのは、問題を列挙して解決を利用者へ委ねるレビューではなく、レビュアー自身が解決を考え、推奨と理由を示し、利用者に残る判断を明らかにするレビューである。

現行本文には根拠付き指摘、判定、戻り先の要求がある。一方、利用者が判断できる説明の順序、推奨と利用者判断の関係は明示されていない。この不足が実際の回答を生んだという因果関係は仮説であり、当時の回答全文による再現確認は未実施。

## 利用者・目的

主利用者は設計レビューを依頼し、その結果で判断する人。今回の直接の利用者はIssue起票者。

**P-01：レビューを読んだ利用者が、何が問題か、レビュアーが何を勧めるか、自分は何を判断し、次に何をすればよいかを理解できる。**

共通目的は、安心して保守し、継続的に改善できる設計を一緒に目指すこと。変更容易性と3Sは推奨理由を具体化する判断軸であり、P-01に代わる目的ではない。

## 対象範囲

- 技術設計レビューの結論・指摘・推奨・判断依頼・次の行動の説明。
- 優先事項が指定されていない場合の変更容易性と3Sの扱い。
- 判定の意味、影響範囲、試作で確かめる事項の説明。
- 説明の分かりやすさと、既存の根拠・安全・独立性・判断権を両立する検証。

対象外：スキルの改名、UI設計レビューへの拡張、他スキルの全面改修、技術設計そのものの自動修正、全案件への3Sチェック表の強制、判定基準の緩和。2026-09-27の追加依頼により、スキル修正・隔離検証・問題がなければPR作成とマージまでを対象とする。

## 要件

すべてP-01に対応する。S番号は末尾の根拠を参照。

| ID | 成立すべき条件 | 根拠 |
| --- | --- | --- |
| R-01 | 最初に平易な言葉で結論と対象範囲が分かる。専門語や判定名が必要なら意味を説明した後に添える | S1、S2 |
| R-02 | 重要な指摘から、発生条件・具体的な困りごと・根拠を読み取れる。理解に必要なら具体例を添える | S1、S2、S5 |
| R-03 | レビュアーは指摘に対して推奨する進め方と理由を示す。根拠不足なら不足と、それを確かめる一歩を示し、案を断定しない | S2 |
| R-04 | 利用者の判断が必要なら、何を決めるか、推奨、選択による影響を具体化する。事実確認と承認を区別し、不要な判断依頼や取得済み承認の聞き直しをしない | S2、S5 |
| R-05 | 次に誰が何を行うか、その前提と確認方法が分かる。工程名だけで終わらず、今できることと確認後に決めることを必要に応じて分ける | S1、S2 |
| R-06 | 明示の優先事項がなければ変更容易性を重視し、関連する3Sを具体的な変更・脅威・規模と結び付けて推奨する。正しさ・安全性を守り、利用先の方針を優先する | S3、S5 |
| R-07 | 平易な説明でも、判定の根拠・限界・未決事項・重大な問題を保持する。推奨を採用済みや実装許可へ変換しない | S2、S5 |

## 受入条件

以下は合意方針を観測可能に具体化した受入条件案。スキル改善後に実行するもので、現時点の合格結果ではない。

| ID | 対象要件 | 前提・操作 | 観測できる期待結果 |
| --- | --- | --- | --- |
| AC-01 | R-01、R-02 | 業務ルール不足の設計をレビューする | 冒頭から不足の内容と影響が読める。「BLOCKED」「domain-modeling」の語を理解しなくても問題を説明できる |
| AC-02 | R-02、R-03 | 根拠のある設計欠陥を提示する | どの条件で誰が困るか、推奨する修正方向とその理由がつながる。単なる原則名の列挙で終わらない |
| AC-03 | R-03、R-04、R-07 | 利用者の業務判断が残るケースを提示する | 推奨は示すが採用済みにせず、利用者が選ぶ事項と影響を特定できる。事実が不足する場合は確認事項として区別する |
| AC-04 | R-04、R-05 | 業務方針が既に合意され、技術上の修正だけ必要なケースを提示する | 同じ方針の承認を求めず、レビュアーが修正方向・理由・次の担当作業を示す。レビューのみの依頼では変更を実行しない |
| AC-05 | R-05、R-07 | 性能を試作で測る必要があり、本番方式は未確定のケースを提示する | 試作で確認する事項、試作の範囲・前提、結果を見て決める内容を区別する。未検証を成功とせず、一律の全面停止とも説明しない |
| AC-06 | R-06 | 優先事項指定なしと、明示指定ありの設計をそれぞれレビューする | 前者では変更容易性と関連する3Sを根拠に推奨する。後者では指定を尊重する。規模・脅威・将来要件を創作して構造を増やさない |
| AC-07 | R-01、R-04、R-07 | 重大欠陥、判定材料不足、受容済みの軽微条件、問題なしをそれぞれ提示する | 各判定と平易な結論が矛盾しない。重大欠陥を説明の都合で軽微化せず、材料不足を欠陥と断定せず、受容済み条件を再承認させない |
| AC-08 | R-01〜R-07 | 生成した回答を利用者が追加説明なしで読む | 「問題」「推奨と理由」「自分の判断の有無と内容」「次の一歩」を回答内容に沿って言い直せる。言い直せなければ表現を見直す。意見が違うことは理解失敗と扱わない |

AC-01〜07は回答の性質を確認する。**AC-08の利用者による理解確認をせず、実利用での価値を達成したとは主張しない。2026-09-27の利用者指示により、AC-08はマージ後の実利用観察とし、隔離検証と品質チェックをPR・マージの条件とする。** 文字数や質問回数の削減だけを成功条件にしない。必要な業務確認を省略して合格を狙わない。

## 制約・依存

- 名称・担当範囲は `technical-design-review` のまま。`ui-design`、`technical-design`、`deep-review` と区別する。
- 既存の対象版・独立性・根拠・受容記録・再レビューの扱いを保つ。PASSは実装許可ではない。
- 3Sを『セキュア・バイ・デザイン』が提唱する統一原則や、変更容易性の保証とは記述しない。
- 利用先の明示方針・既存規約を無視してupstream固有の価値観を押し付けない。
- 当該スキルを利用可能にするために、Yohaku等の追加導入を必須にしない。
