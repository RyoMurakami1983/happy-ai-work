# Domain Model 010：レビューを判断と行動につなぐ

2026-09-26 / v1 / モデル案

## 目的・範囲

[PRD](../prd/010_PRD.md)のP-01とR-01〜R-07を根拠に、技術設計レビューにおける情報と責任をモデル化する。ソフトウェアのクラスやサービスを作るためのモデルではなく、レビューの説明で何を区別し、誰が決めるかを定める。

現行スキルには「指摘」「判定」「戻り先」がある。今回のモデル案は、そこへ「推奨」「利用者への確認・判断依頼」「次の行動」の関係を明示する。用語の入口は[CONTEXT](../../CONTEXT.md)。業務条件や設計対象の要件そのものは、このモデルで新設しない。

## 主体と責任

| 主体 | 責任 | 境界 |
| --- | --- | --- |
| レビュアー | 根拠から問題を判断し、解決方向を検討し、理由付きの推奨と必要な問い・次の行動を提示する | 利用者の価値判断や未合意の業務ルールを採用済みにしない。レビューだけの依頼では修正しない |
| レビュイー（利用者） | 必要な業務事実を補い、自分に属する優先順位・受容・案の採否を判断する | 技術的な意味の解読や解決策の発明を、説明不足のまま任されない |
| 解消担当 | 業務条件の明確化、設計修正、試作・確認など、割り当てられた問題解消を行う | 担当は役割で指定できる。利用者がすべての作業を行うとは限らない |

推奨と評価の根拠はレビュアーが持つ。要件の採否と人間に属する判断は利用者が持つ。技術的に妥当な推奨があることと、実行の許可があることを分ける。

## 概念モデル

| モデル | 保持する意味・振る舞い | 対応要件 |
| --- | --- | --- |
| M-01 レビュー評価 | 対象版、確認範囲、根拠、判定、限界。何を評価でき、何を評価できないかを示す | R-01、R-07 |
| M-02 レビュー論点 | 指摘または未確認事項、発生条件、影響、関連要件。問題と単なる質問を分ける | R-02、R-07 |
| M-03 推奨 | 勧める対応、理由、成立条件、必要な不利益・推奨が変わる条件。資料不足なら確認方法を勧める | R-03、R-06 |
| M-04 利用者への依頼 | 事実確認または判断依頼。問い、必要な理由、答えによって変わる箇所を持つ | R-04 |
| M-05 次の行動 | 解消担当、具体的な作業、前提、確認方法。今できるか、何の確認を待つかを示す | R-05 |

関係は「評価 → 論点 → 推奨 → 必要な依頼／次の行動」。一つの推奨が複数の論点を解消することもある。問題なしなら論点・依頼を作る必要はない。論点ごとに必ず質問を作るモデルではない。

3Sは推奨の理由を検討する観点であり、別の判定や点数を持つモデルにしない。Scalableと業務仕様の変更容易性も同義にしない。

## 守る条件

| ID | 条件と成立する範囲 | 責任 | 根拠 |
| --- | --- | --- | --- |
| I-01 | 回答を返す時点で、平易な結論は対象版・範囲・判定と矛盾しない | M-01 | R-01、R-07 |
| I-02 | 問題を指摘するなら、条件・影響・根拠を辿れる。未確認は欠陥が確認されたことを意味しない | M-02 | R-02、R-07 |
| I-03 | 推奨は採用・受容記録が得られるまで推奨である。沈黙や資料内の自己承認で状態を変えない | M-03、M-04 | R-04、R-07 |
| I-04 | 利用者へ判断を求める時点で、何を選ぶかと、その結果の違いを説明できる。既に決定済みなら同じ判断を再要求しない | M-04 | R-04 |
| I-05 | 次の行動を示す時点で、工程名だけでなく具体的作業と担当を特定できる。未確認事項に依存する作業はその依存を隠さない | M-05 | R-05 |
| I-06 | 推奨の検討中と回答時に、明示方針・安全・正しさを既定の変更容易性より優先する。想定のない規模・脅威を事実にしない | M-03 | R-06、R-07 |
| I-07 | 評価・承認・実行・検証を通じ、設計のPASS、利用者の採用、実装許可、検証済みを別の事実として保持する | 全モデル | R-07、既存契約 |

## 操作と状態

| 操作 | 必要な入力・事前条件 | 成功後 | 不足・失敗時 |
| --- | --- | --- | --- |
| 論点を説明する | 評価対象と根拠、要件との対応 | 具体的な条件・影響を伴う説明 | 根拠不足を未知として残し、断定しない |
| 対応を勧める | 論点、既知の方針・制約 | 理由と条件のある推奨 | 案を選べない理由と情報を得る一歩を提示する |
| 利用者に尋ねる | 未解決で利用者の回答が必要な問い | 事実確認か判断依頼かが明確になる | 回答がなくても採用状態へ遷移させない |
| 回答を反映する | 明示回答または既存の根拠ある決定記録 | 事実確認は根拠を更新。判断は採用・非採用・保留として記録し、影響する評価を見直す | 不明確な回答は該当事項だけ未決のまま残す |
| 次の行動へ渡す | 推奨、解消担当、必要な前提 | 具体的な引き継ぎができる | 未確定部分と独立してできる作業を分ける。実行を許可済みにしない |

判断が必要な推奨は「提示 → 利用者の回答待ち → 採用／非採用／保留」となる。事実の確認だけで推奨を採用済みにしない。利用者の判断が不要な場合は回答待ちを挿入せず、評価と次の行動を提示する。これは実装開始の自動許可ではない。

## 正常・境界・拒否の例

| 例 | モデル上の扱い | 対応AC |
| --- | --- | --- |
| 予約競合時の優先ルールが未合意 | M-02で不足を示し、M-03で推奨と理由、M-04で例外の事実確認・方針の判断を区別する | AC-01、AC-03 |
| 一人だけが引き受ける要件は合意済みだが、同時保存で二人が成功する設計 | M-02で欠陥を説明し、M-03で保存境界での保証を勧める。業務方針の再承認は不要 | AC-02、AC-04 |
| 応答速度は実装して測る必要がある | M-05で限定した試作と測定を示す。本番方式の評価完了とは扱わない | AC-05 |
| 設計上の重大な権限漏れがある | 分かりやすい説明でも重大性を維持し、受容の創作や条件付きPASSへの読み替えを拒否する | AC-07 |
| 問題なし・追加判断なし | M-01の確認範囲と結論、必要な次工程だけ示す。質問や指摘を捏造しない | AC-04、AC-07 |

## 境界を分けた理由

指摘と推奨を分けると、解決案を変えても観測された問題は保持できる。推奨と判断依頼を分けると、レビュアーの責任を保ちながら利用者の判断権も守れる。判定と次の行動を分けると、全体の評価が未完了でも、独立して可能な確認作業を説明できる。

これらは説明上の意味の境界であり、別ファイル・別クラス・別サービスへの分割要求ではない。

## 未決事項と引き継ぎ

モデルを成立させるために新たな業務ルールを決める必要はない。利用者の理解効果は未検証。問いの選別・説明順・既存本文への配置は[技術設計](../design/010_TECHNICAL_DESIGN.md)へ渡す。モデルと上流要件の不一致が見つかればPRDへ戻す。
