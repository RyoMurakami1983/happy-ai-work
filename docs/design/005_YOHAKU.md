# Yohakuとhome共通方針の融合

作成日: 2026-09-11

## 目的と採用した判断

利用者から示された「認知負荷最小化スキル設計」の会話を基に、AIの出力を人が正しく理解・判断・行動できる必要十分な形へ整える。Constitution 1.0.0の余白、正確さ、形式知化、外科的対応を具体化する通常改善であり、原則の優先順位は変更しない。公開skillでは利用先の目的と規則を尊重する。

- Yohakuのprimary purposeは、読者に合わせた情報量と見せ方の調整。文章の主張・構成そのものの推敲や、専門領域の実装・調査手順を置き換えない。
- コードの簡素化を依頼されたときだけ専用referenceを読み、既存・標準・基盤・既存依存を検討する。CavemanやPonytailは導入条件にしない。
- 常設部分は`home-bootstrap/assets/AGENTS.md`の既存管理領域へ融合する。目的の「確認」を「把握」へ変え、報告原則を1項目加えた6項目とする。Yohaku用の別マーカーや断片は追加しない。
- 詳細な読者別の説明、比較の型、混乱時の対応、コード簡素化はskillが所有する。home側はYohaku未導入でも有効で、skill側もhome変更を要求しない。
- [ADR 0004](../adr/0004-preview-plugin-distribution.md)に従い、実利用検証中のYohakuを`happy-preview`へ配置する。通常の自動選択を保ち、単純な質問では自動選択しないdescriptionにする。正式採用の候補先は`happy-core`。

読み込みを必要時に分ける構成は[公式のskillガイド](https://learn.chatgpt.com/docs/build-skills)、homeとrepoの役割分離は[公式のAGENTS.mdガイド](https://learn.chatgpt.com/docs/agent-configuration/agents-md)とも整合させる。

## 省略の条件を具体化する判断（2026-09-19）

利用者が示した「日本文化武道の美」の会話を設計の手掛かりとし、Yohakuの省略を、必要な意味・働き・備え・利用者の選択権を保ちながら、不要な説明や重複を減らすことと捉える。読み手が自分で判断する余地を保ち、判断に必要な情報を推測させる短縮は採用しない。美しさを独立した最適化目標にせず、用語・順序・情報の関係が整った結果として扱う。これは本skillの設計上の解釈であり、日本文化や武道に共通する教義とは位置付けない。

Y-01・Y-02・Y-03・Y-05を実行時に判断しやすくするため、「内容を決めてから整える」の4〜5を置き換える。必要な意味を残す判断と、短い表現に変える判断を分け、関連する補足を後段へ移せる条件、操作前に必要な警告を残す条件を明確にする。短縮によって主語・条件・手順のつながりを読み手が補う必要が生じた場合は戻す。学習説明では必要な因果関係を残し、答えだけの依頼には説明を増やさない。

表現整理は、明示要件、条件の位置、説明のつながり、不要な重複を確認できた時点で終える。依頼された調査・実装・検証の完了とは区別する。全文の分類、固定の出力形式、美しさの採点、通常の言い換えごとの追加承認は要求しない。コード簡素化reference、継続適用、home設定の契約は今回の変更対象に含めない。

## 受入条件

| ID | 観察できる完了条件 |
| --- | --- |
| Y-01 | 読者と目的に応じて順序・説明量を変え、複数の依頼や指定書式を保持する |
| Y-02 | 否定、例外、数値・単位、順序、安全条件、不確かさ、判断に必要な代替案を落とさない |
| Y-03 | 「分からない」には例や段階説明で応じ、長文・詳細の依頼を勝手に要約しない |
| Y-04 | コード変更は依頼範囲だけで行い、検証・認可・データ保護を短縮のために削らない |
| Y-05 | 一行で答えられる質問へ不要な手順・見出し・続行確認を付けない |
| Y-06 | 明示呼び出し後は同じタスクの後続依頼にも適用し、利用者による範囲限定・解除を優先する。自動選択だけの場合や別タスクへ継続範囲を広げない |
| Y-07 | 作成できる引き継ぎには適用状態・スキルの場所・主要原則を残し、再開後は最新の指示を確認して必要時だけ再読する。完全保持を保証せず、常設設定や毎回答の確認を増やさない |
| Y-08 | 必要な意味を保って言い換え、結論を変える条件や操作前の注意を該当箇所に残す。補足の移動や重複削除で読み手に条件・手順を推測させない |
| Y-09 | 独立して読まれる操作手順では、その操作前に必要な警告を重複だけを理由に削らない。引用・コマンド・識別子・指定の語調を保つ |
| Y-10 | 明示要件・条件の位置・説明のつながり・不要な重複を確認できたら表現整理を終える。追加承認や続行確認を増やさず、依頼された作業・検証は完了する |
| H-01 | 管理領域が6項目に融合され、詳細なYohaku規則や別マーカーを常設しない |
| H-02 | 更新時に管理外の内容・空白・改行を保持し、同じテンプレートの再適用で差分が増えない |
| H-03 | dry-runは書き込まず、適用時は元のファイル内容をbackupへ保持する |
| H-04 | skill改善と実homeへの適用を区別し、適用済みの承認を聞き直さない。実homeの変更は対象・差分と承認範囲に従う |

H-02とH-03は既存の「管理領域だけ更新」「既存内容とbackupを保持」という契約を根拠にする。旧実装は領域前後の空白を整形し、ファイル先頭の領域へ空行を加えていた。マーカー間だけの置換と、読み書き・backupで改行変換をしない処理へ修正する。

home-bootstrapのGit案内は初回導入とGit設定の依頼時に残す。既存の共通方針だけの更新でGit設定の全文を再提示する挙動は、今回の依頼に必要な情報へ絞る目的から外す。Hooksの個別承認境界は維持する。

## 明示呼び出し後の継続

後続の依頼で、利用者は「タスクの最初に自分でYohakuを呼び、そのタスク中と文脈圧縮後にも方針を残したい」と明確化し、完全な保持保証は求めないとした。これをY-06・Y-07の根拠として、継続・解除・必要時の再読をスキル自身へ追加する。

継続範囲は同じタスク（会話）とし、一つの回答を終えただけでは解除しない。適用範囲の明示・解除は古い引き継ぎより優先する。短い質問には短く答え、領域skillの併用や詳しい説明の依頼とも両立させる。自動選択は当該依頼に限り、明示呼び出しによる継続と区別する。

引き継ぎを作れるときに状態・参照先・主要原則を残し、継続の手掛かりがある場合に必要な本文を再読する。永続メモリや自動起動の実装ではなく、保持された文脈から復元しやすくする指示として扱う。AGENTS.mdへの開始指示追加、常駐処理、毎回答の再読・告知・確認は採用しない。既に融合したhomeの6項目とは別の変更である。

この追記の実際の文脈圧縮を挟んだ継続動作は、今後の試用で確認する。以下の8件の模擬依頼は追記前の回答調整の確認であり、圧縮後の保持を検証したものではない。

## 模擬依頼の確認範囲

skill-creatorの独立forward-testingを用い、作成担当者の会話・設計書を渡さずに架空の8依頼へ回答する。正式な効果比較や自動選択率の測定ではなく、試用前の小規模な動作確認とする。

| 依頼 | 見る境界 |
| --- | --- |
| 部長向けの障害報告 | 影響件数・復旧状態と、原因や欠損の未確認を区別できるか |
| 予算と復旧時間が両立しない二案 | 満たさない条件を隠して一案に決めないか |
| 再試行が分からない初心者 | 具体例で説明を補い、二重送信の危険を残せるか |
| 指定した6項目の詳細な設計説明 | 指定形式と必要な完全性を短縮しないか |
| 検証環境だけで行う不可逆な削除手順 | 本番禁止・順序・残す設定・完了条件を保持できるか |
| 保存処理を短くするコード例 | 保存先の境界検証を削らず、依頼のないファイル操作をしないか |
| 答えだけ求める掛け算 | 不要なskill手順を持ち込まないか |
| home配布テンプレートだけの改善 | 実home適用やGit設定へ広げないか |

2026-09-11の独立確認では、障害報告の未確認事項、比較案の条件不成立、再試行の具体例、指定6項目、安全な手順、保存先の境界チェックを保つ回答が得られた。掛け算には答えだけを返し、テンプレート改善では実homeを変更しなかった。テンプレートの5項目への再融合案も出たが、項目数の固定を試す依頼ではなく、今回採用した配布物は6項目を維持する。

確認者からhome-bootstrap冒頭の「まずdry-run」が配布物の編集にも読めるとの指摘があり、実homeへの導入・更新に限る手順だと先に明記した。周辺の個人設定を読む対象も実home適用時に限定した。修正後に同じ確認者が再読し、両方の適用範囲が明確になったことを確認した。これは小規模な模擬応答と指示の確認であり、実利用や正式な比較評価の合格を意味しない。

## 実利用で確認すること

省略条件の変更では、次の5件を追加の模擬依頼とする。Y-08〜Y-10は既存条件の具体化であり、過去の確認結果は変更しない。

| 依頼 | 観察する境界 |
| --- | --- |
| 試作品10台は正常、量産に必要な温度試験は未実施という報告を短くする | 台数・未実施・採用条件を残し、量産可否と条件を一緒に読めるか |
| 原因・影響・復旧の説明が繰り返される障害報告を整理する | 必要な意味と正確な引用・識別子を保ち、重複だけを減らせるか |
| 別々に配布する2枚の操作カードを短くする | それぞれの対象・前提・順序・完了条件と、操作前の警告を残せるか |
| 初心者への仕組みの説明と、答えだけ求める計算に応じる | 前者の因果関係と具体例を保ち、後者には説明を増やさないか |
| 小さな文書修正と指定の検証を実行し、結果だけを報告する | 修正・検証を実行し、不要な続行確認なしで終えられるか |

同じモデル・設定・依頼で変更前後を確認し、重大な欠落、不要な確認、依頼の未完了を観察する。小規模な模擬依頼から認知負荷の改善率、自動選択率、実利用での効果は断定しない。回答から観察できる終了の仕方と、モデル内部の検討回数も区別する。

代表的な実作業で、重要条件の見落とし、読み直し、追加質問、正しい判断・行動までの時間を観察する。可能なら同じ条件で現行方針、融合したhome方針、home方針とYohakuを比較し、文字数・コード行数は補助指標にする。正確さ・安全・明示要件を落とした短縮は不採用とする。

認知負荷や改善率は未測定。会話中の「約80%」は予測であり、実証済みの性能や採用基準へ取り込まない。「8件で中央値15%改善」も未採用の基準案として扱う。正式な比較評価を行う場合は、実行前に条件とrubricを固定し、[評価資産の契約](../EVALUATION_ASSETS.md)に従う。

初期案の常設5項目の別途追記と`AGENTS.fragment.md`の配布は、後続会話の融合方針で置き換えた。会話で言及されたダウンロード成果物は今回取得しておらず、確認できた会話本文から作成した。
