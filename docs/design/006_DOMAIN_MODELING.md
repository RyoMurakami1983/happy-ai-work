# Domain Modelingの責務と成果物

## 目的と根拠

`domain-modeling`を、用語の整備に加えて、合意済み要件を守るモデル・業務ルール・不変条件・状態遷移を残せるskillへ再定義する。

依頼の根拠は2026-09-22の「設計レビュースキル整理」を踏まえた再定義依頼と、その参照会話のB節。会話に添付された「目的駆動設計とAIコードレビュー — 書籍・動画からの蒸留資料 v1.0」の3.2〜3.5、4.2、5.3〜5.4も判断材料とした。資料の全文や一時保存先は配布物へ複製しない。

既存版は「モデル構築」と「用語の正規化」が混在し、新しい問いを禁止しながら反例による検証を求めていた。保存先は用語集と技術ADRに寄り、モデルの業務上の契約を残す場所が不足していた。

これは現行Constitution内の通常改善であり、原則・評価境界・所有権は変更しない。

## 採用する責任分担

| 所有者 | 責任 |
| --- | --- |
| `interview-with-docs` | 根拠の収集、業務事実・矛盾・未知の深掘り、合意済み用語の整理 |
| `to-prd` | 目的・要件・ACの正本、モデリングで見つかった要求不足の回収 |
| `domain-modeling` | 目的・要件に対応する用語、モデル、意味の境界、業務上の契約 |
| `technical-design` | module、public interface、DB・通信・deploy等の技術構造 |

問いや反例の作成はモデリングに必要である。未合意の答えを新しい製品要件として採用することは含めない。既存コードの挙動と合意済み要求が違う場合は、どちらかを黙って優先せず差異を返す。

## 成果物と配置

- Vocabulary passは既存の用語正本を保守する。正式なPRDやモデル文書を必須にしない。
- Formal modelingは既存のドメイン文書、なければ`docs/domain/NNN_DOMAIN_MODEL.md`に記録する。PRDの既存IDと参照を保ち、要件の重複管理を避ける。
- `CONTEXT.md`の既存のMission等は保持し、詳細な契約を詰め込まない。複数文脈の同名語を一つに統合しない。
- ADRは長期的なドメイン境界・業務責任の理由を扱う。既存referenceの技術選定・通信方式の例はこのskillの責務から外す。
- `interview-with-docs`の呼出箇所だけを処理レベルに合わせる。全体の工程再編や新しい設計レビュースキルの作成は今回の対象外。

## 受け入れ条件

1. 用語だけの依頼は用語集の局所更新で終え、既存の非用語情報を保持できる。
2. 合意済み要件から、モデルの責任・境界・不変条件・操作前後の条件を根拠付きで記録できる。
3. 未決の数量上限・権限・状態遷移等を発明せず、影響と戻り先を明示できる。
4. 現行コードを要求の正本にせず、差異を業務事実または要求の確認へ返せる。
5. 単純CRUDや異なる文脈の同名概念へ、不要なモデル分割・統一・技術選定を強制しない。
6. 一般的な記憶依頼や技術ADRだけの依頼をモデル作成に広げない。

## 実行規約への対応

| 対象 | 根拠・必要性 |
| --- | --- |
| `domain-modeling/SKILL.md` | 条件1〜6を、起動境界・処理レベル・上流への戻り方として保持する |
| `CONTEXT-FORMAT.md` | 条件1・5のため、既存構造と文脈ごとの意味を保つ |
| `DOMAIN-MODEL-FORMAT.md` | 条件2〜4の成果物を再利用できる形にし、未決と確定を分ける |
| `ADR-FORMAT.md` | 条件5・6のため、ドメイン判断と技術判断の所有者を分ける |
| `interview-with-docs/SKILL.md` | 条件1・3のため、用語整理の呼出しが無条件の正式モデリングにならないようにする |
| `implementation-plan/references/WORK_ARTIFACTS.md` | モデル文書の保存先と案件番号を、工程間で共有する成果物一覧へ反映する |

## 検証方針

公式`skill-creator`の構造検証、repoの品質検証に加え、用語整理・合意済みモデル・要件不足・単純CRUD／技術ADRの合成事例で独立したforward-testを行う。基準はこの受け入れ条件を実行前に固定し、過去の評価recordは変更しない。これは限定的な挙動確認であり、実案件での改善効果や未見事例への一般化を証明するものではない。

## 検証結果（2026-09-22）

- 公式`quick_validate.py`は`domain-modeling`と呼出箇所を変更した`interview-with-docs`で成功。
- `uv run --offline --script scripts/validate_quality.py --offline`は成功。repo validator、62件のunit test、Ruff、ty、差分の空白検査を通過した。既存のADR記録契約は、技術判断を`technical-design`へ引き継ぐ場合にも維持した。
- 固定した6つの合成事例を、実装者とは別の生成担当2名と評価担当1名で確認。用語整理、合意済みモデル、要件不足、単純CRUD、技術ADRの5件はPASS。一般的な記憶依頼は成果物内容が適合したが、home・他repoへの非書込みを独立に監査できずB（証拠不足）。生成担当の「外部変更なし」という自己申告だけでPASSへ変えなかった。
- ADRの記録義務を補足した最終版では、影響する技術ADR事例を別runで再実行してPASS。初回結果と混ぜず保存した。実行入力・版のhash・生成物・判定はgit対象外の`docs/local_skill_evals/domain-modeling-20260922/`に保持し、既存recordは変更していない。
