# ゲーム制作の2つのskill

作成日: 2026-09-06

## 目的と配置

ゲーム制作経験のない利用者が、根拠ある設計判断とUnityでの実装を別々に依頼できるようにする。[ADR 0004](../adr/0004-preview-plugin-distribution.md)の採用により、`happy-preview`に`video-game-design`と`unity-beginner-development`を置く。新pluginをmarketplaceへ追加し、通常の`happy-coding`とは分けて試用する。正式採用時の移動先候補は`happy-coding`。

依頼で示された目的は、宮本茂を主軸とし10名以上の制作者の知見と暗黙知・第三者分析を活用する設計skill、および初心者向けUnity開発skillの作成。子ども向けゲームを主要な利用例にする。対象を子どもだけに限定する回答はまだ得ていないため、汎用の目的と子ども・家族向けreferenceを分けた。共有会話の初作品向け規模案は例として扱い、2D・1画面・日数を恒久条件にしない。

## 設計上の判断

- 設計skillは遊びの仮説とプレイ観察を担当し、実装skillはEditor・component・asset・入力・実行検証を担当する。一般UI、一般.NET、工程管理の既存skillと責務を分ける。
- 名言集ではなく、根拠・今回試す判断・適用限界を持つ14名のカードを用意する。本人発言、共同開発者の証言、制作記録、第三者分析、スキルの推定を区別する。
- 上田の資料は本人発言の翻訳として原語未照合を残す。横井の逸話は伝聞と開発当事者証言を分ける。宮本の観察・身体動作の記録は証言者を明記する。
- 面白さや学習効果を本人の権威や技術テストから認定しない。人による観察なしでは仮説として渡す。
- UnityのEditor／package版を恒久固定しない。project契約と対象版の公式資料を確認する。特定環境で検証できなかったことはskillの機能制限へ一般化しない。

## 調査と確認の範囲

複数エージェントで初回の人物・Unity資料調査を分担し、次巡で弱い帰属、第三者分析の限界、入力・保存・検証条件を再確認した。根拠URLと採用した要約は各skillのreferencesを正本とする。

その後、独立エージェントへスキルを渡し、以下の模擬依頼に対する回答を生成した。

| 模擬依頼 | 観測した回答 |
| --- | --- |
| 勝敗のない3D庭づくりの設計 | 3Dと勝敗なしを保持し、配置・交代の仮説、観察方法、未試遊の状態を明記した |
| legacy入力をFixedUpdateで読むジャンプ不具合、Editor不在 | Updateで押下を保持し物理更新で消費する最小例と接続・操作手順を提示し、Unity実行未確認を明記した |

これは2つの回答例による動作確認であり、人のプレイテスト、実Unity projectでの検証、発火精度の実測、固定rubricによる正式な比較評価ではない。別の静的レビューで起動境界・参照・帰属を確認し、PDFのページ指定誤りを修正した。
