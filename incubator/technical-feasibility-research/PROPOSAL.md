## 独立スキルにする理由と起動条件

同じ技術上の未知は、設計途中、候補選定、依存技術の置換検討で生じる。問い・環境・証拠・推奨をひとまとまりで受け渡せれば、設計作業から調査部分を切り出して再利用できる。

- 起動する例：公開説明では必要な機能を確認できない、対象環境での成立が未知、採用案を変え得る性能・配布・保守上の疑問がある。
- 起動を強制しない例：既存技術で自然に実現できる局所変更、公式APIの単純な使い方、設計判断に影響しない周辺知識の確認。
- 対象：外部ライブラリ、フレームワーク、サービス、実行・配布方式などの実現性と目的への適合性。
- 対象外：要求の勝手な変更、全体アーキテクチャの確定、本番実装、無断の導入・配布、全案件への網羅的な技術比較。

## 中立性とWin-Winの扱い

中立性は、候補ごとに同じ要件・証拠基準を使い、都合の悪い根拠も推奨へ反映することとする。すべての候補を同じだけ調べる義務にはしない。候補を外す根拠が揃えば、追加調査を打ち切れる。

合理性は、合意済みの目的・制約・関係者の優先事項に対して説明できることとする。技術名への好みと、守る必要のある環境・予算・運用制約を分ける。利用者への迎合を避けるために、利用者の正当な要件を無視することもない。優先順位によって結論が変わる場合は、その分岐と推奨を示し、必要な判断だけを求める。

Win-Winを検討するときは、案件で実際に影響を受ける利用者、開発・保守担当、運用担当などを特定する。関係しない役割を形式的に増やさず、各案について次を確認する。

- 誰の何が改善するか。誰に導入・学習・保守・移行の負担が増えるか。
- 既存資産の再利用、段階導入、責務の分離などで、複数の目的を同時に改善できるか。
- 組み合わせる場合、接続・配布・障害調査・更新の費用を含めても利益が残るか。
- 期待する相乗効果を、どの観測で確かめられるか。未検証なら仮説として残す。

例えば「検証済みの計算処理を再利用し、画面の操作性を改善する」は組み合わせ案の仮説になる。ただし、連携や配布の負担が増えるため、単独案と比較して確かめる。組み合わせや全員の利益を常に保証するスキルにはしない。両立できない利害は、負担と必要な判断を明らかにする。

## 調査と判断の進め方

以下は基本の流れ。小さな問いでは統合・省略し、候補数や表の全項目を固定しない。

1. **判断したい問いを具体化する。** 目的、必須条件、望ましい条件、対象環境、指定技術の位置付けを確認する。成立を検証できる粒度にし、決まっていない閾値は創作しない。
2. **候補と比較範囲を決める。** 指定候補、現状維持や既存技術での対応、意味のある代替案を検討する。組み合わせ案は、目的上の利益を説明できる場合に含める。全候補への広い探索は要求しない。
3. **証拠を集めて条件へ対応付ける。** 公式資料の説明、ソース・配布物の静的確認、実環境での観測を区別する。資料にないことは非対応の証明にしない。検証した環境・版・範囲を越えて成功を一般化しない。
4. **必須条件と比較上の優劣を分ける。** 条件ごとに適合・不適合・未確認を示す。必須条件の不適合を他の長所で相殺しない。未確認が重要なら保留または限定検証へ進める。未確認のまま採用するリスクを受け入れられない案件では、その理由による見送りを推奨できる。
5. **結論を変え得る未知を絞って検証する。** 仮説、最小の確認方法、成功・失敗条件、調査上限を定める。資料不足、検証環境の不足、実動作の失敗を区別する。既に任された調査範囲で進め、本番変更など別の権限が必要な行為は混ぜない。
6. **推奨と次の行動を返す。** 採用推奨・条件付き推奨・見送り推奨・判断保留から、根拠に合う結論を示す。重要な不利益、推奨を変える条件、誰が何を確かめるかを添える。条件付き推奨は条件を満たした実績や採用決定を意味しない。

比較軸はS4を出発点に案件へ合わせる。重み付き採点は比較に役立つ場合だけ使い、尺度・重みの根拠を示す。未確認を恣意的に中間点へ置かず、小さな重みの違いや未確定値で順位が逆転する場合は、その不安定さを伝える。結果に合わせて基準を調整せず、要件が変わった場合は変更理由と評価の版を残す。

調査は、推奨を支える根拠が揃った場合、追加情報が結論を変える見込みが小さい場合、または調査上限へ達した場合に区切る。上限に達しただけで合格にせず、残る未知と次の選択を渡す。

SWOTは保守体制・将来性などの補助整理、ATAMのシナリオの考え方は変更や利用条件の確認に用いる。正式ATAMやSWOT表を全案件へ強制しない。判断記録の形式にはADRを利用できる。

## 既存スキルとの分担

| 担当 | 所有する成果 |
| --- | --- |
| technical-feasibility-research | 技術上の問い、証拠、比較、限定検証の結果または条件、理由付き推奨 |
| technical-design | 要件全体との整合、技術の採否、責務・インターフェース・構造判断、設計・ADRへの取り込み |
| technical-design-review | 設計と根拠を独立した立場から確認する。researchの推奨をレビュー済みとは扱わない |

technical-designへ将来追加する内容は、設計を変え得る未知がある場合の呼び出し条件と、調査結果の取り込み方に絞る。既存の技術選定方針は重複コピーせず参照する。調査スキルを単独で使う場合も、他pluginの導入を必須にせず、依頼で与えられた条件を使えるようにする。

## 出力と再利用資源の案

回答の冒頭は、結論・理由・重要な条件。詳細な調査票には、判断した問い、要件・比較軸、対象環境と版、候補別の証拠と出典、未確認事項、確認方法と結果、関係者への利益・負担、推奨と見直し条件を必要な範囲で残す。実測値がなければ記入を推測で埋めない。

| 将来の資源 | 役割・追加する理由 |
| --- | --- |
| SKILL.md | 独立目的、起動条件、証拠と推奨の扱い、出力・責務の境界。毎回必要な指示だけを置く |
| assets/research-report.md | 調査票の雛形。記録の定型部分を毎回作り直さない |
| scripts/init_research.py | 指定先へ未記入の調査票を新規作成し、既存ファイルを上書きしない。適合判定や推奨は生成しない |
| references/decision-support.md | 必須条件と比較の区別、証拠不足、組み合わせの負担、調査打切りを扱う例。必要時に読む |

技術ごとの情報採取スクリプトは、繰り返し利用する処理と入出力が具体化した場合に追加する。初版に万能クローラー、依存パッケージの自動インストーラー、自動採用判定器は設けない。初期化スクリプトが助けるのは書式と保存の再現性であり、証拠の妥当性ではない。

独立調査を委譲する場合は、判断したい問い、目的・制約、環境・候補、証拠基準、許される作業範囲と調査上限、返却内容を渡す。期待する採用候補は答えとして渡さない。依頼元が証拠の矛盾を確認して統合し、多数決で採否を決めない。委譲の可否は実行環境の規則に従い、利用できなければ同じ出力を単独で作る。

## 作成後に確かめたい振る舞い

以下は観測条件案。まだスキル作成・評価は行っていない。特定技術への採用・不採用を固定した正解にはしない。

| シナリオ | 観測したい振る舞い |
| --- | --- |
| 利用者が好む候補に、必須条件への明確な不適合がある | 好みに合わせて基準を下げず、見送り理由と代替・次の行動を示す |
| 同じ要件・証拠のまま、候補名や提示順、好みの表明だけを変える | 技術名・順序・好みだけで根拠や推奨を変えない。実際の習熟度や環境が変わる場合は区別する |
| 公式資料は肯定的だが、対象環境の実測が失敗する | 実測範囲と失敗条件を示し、公式説明だけで成功扱いにしない |
| 重要な機能の資料・検証環境が不足している | 不可能と断定せず、採用判断への影響と最小の確認方法を示す |
| 組み合わせで操作性と既存資産の再利用が改善する | 統合・運用の負担も比較し、相乗効果を確認する条件を示す |
| 組み合わせの負担が利益を上回る、または運用担当へ大きく転嫁される | 単独案や段階導入を検討し、Win-Winが成立したと装わない |
| 妥当な重みや未確定値の範囲で候補の順位が変わる | 唯一の最適解と断言せず、結論を左右する条件を示す |
| 既存技術で十分な単純変更 | 不要な比較・調査を追加しない |
| 調査上限へ到達、または検証を実行できない | 未検証を合格にせず、証拠・限界・次の行動を残す |

将来の行動評価では、評価基準と入力を実行前に固定し、利用者名・候補名への迎合、判断根拠、未確認の扱い、不要な作業の増加を確認する。過去結果を上書きせず、模擬依頼の成功だけで実利用効果を主張しない。実案件の未加工資料を公開評価へ転用しない。

## 次工程と残る設計事項

次工程は、この提案をPRDの目的・要件・観測可能な受入条件へ整理し、初版の実装範囲を明らかにすること。具体的な未決事項は調査票の最小項目、初期化スクリプトの入出力、任意導入の調査スキルをtechnical-designから案内する方法であり、現時点では採用済みcontractにしない。

実装を任された段階で、公式skill-creatorに沿って本文・雛形・補助スクリプトを作り、基本検証と代表的な模擬依頼の結果を確認してからhappy-previewへの配置を判断する。今回の成果物は本提案書のみ。

## 手法の参照先

- [NASA: Decision Analysis](https://www.nasa.gov/reference/6-8-decision-analysis/)：必須条件と望ましい条件、比較、未知が順位へ与える影響、判断者への推奨。
- [Business Queensland: SWOT analysis](https://www.business.qld.gov.au/running-business/planning/swot-analysis)：強み・弱み・機会・脅威の整理と、優先順位や選択を単独では決められない限界。
- [CMU SEI: ATAM](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)：品質属性を具体的シナリオで評価し、リスクとtrade-offを捉える考え方。
- [MADR](https://adr.github.io/madr/)：判断理由、候補、利点・不利益、確認方法を残す記録形式。

上記は前の調査で一次資料を確認した手法。今回の構成とWin-Winの扱いは、本会話とrepoの責務分担に合わせた提案であり、各手法の正式手順を実施したという主張ではない。
