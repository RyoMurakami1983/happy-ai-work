# 余白

**大切なものに絞り、次に考え、選び、新しく挑戦できる余地を残しているか。**

少なければよいのではなく、必要なものが十分にあり、必要でないもので埋め尽くされていないこと。空きそのものではなく、人が理解・判断し、変化へ応じられる余地を品質として見る。

## 見極めること

- **大切なものが中心にあるか**: 何を満たすための内容・機能・作業か。単に追加できるからと詰め込まず、目的に不可欠なものを見失わない。
- **次へ向かう余地があるか**: 読み手が考える、使い手が選ぶ、作り手が試す・直すための余力が残っているか。目先の要求をすべて満たすことで、学習や新しい挑戦を閉ざしていないか。
- **不足を余白と呼んでいないか**: 必要な意味・機能・責任を落とし、相手の推測や後始末に押し付けていないか。安全条件、根拠、明示要件、必要な検証・修復手段は守る。

詰め込んだ案と削りすぎた案のどちらでもなく、目的を満たしながら次の判断・行動の余地を残す案を選ぶ。固定の空き率、文字数、機能数で判定しない。納期や責任を無視して余裕だけを優先する軸でもない。

## 実務への組み込み

実務skillの設計・執筆・計画・レビューなどの判断場面から参照する。毎回の質問や別の評価儀式を増やさず、対象の目的と制約に照らして使う。明示された適用範囲と後からの解除を守り、別タスクへの常時適用やhome設定変更を推定しない。

| 対象 | 判断の例 |
| --- | --- |
| 文章・説明 | 結論や条件が埋もれていないか。読み手が理解して考えられるか。短縮で意味が欠けるなら説明を残す、または足す |
| 設計・コード | 今の要件を満たし、理解・検証・修復できるか。将来の仮定で機能を詰め込まず、変更の余地を残せるか |
| 作業・計画 | 必要な成果と責任を果たしつつ、見直し・学習・新しい試行を受け入れられるか。全てを同時に抱える前提になっていないか |

`短歌と俳句`は必要な意味を薄めず表現・構造を研ぐ軸、`余白`は必要十分な内容と次の可能性を保つ軸。両方を使えるが、文章短縮だけに余白を限定しない。具体的な編集・実装・改善の手順と許可は実務skillや依頼に従う。コードの簡素化が依頼範囲にある場合の補助観点は[code-simplicity.md](references/code-simplicity.md)を参照する。

## 過程と結果で確かめる

- 過程: 何を大切として残し、何を増やさない・減らすと判断したか。その理由を目的・制約に結び付けられるか。
- 結果: 必要な理解・機能・責任を損なわず、何を考える・選ぶ・変える・試す余地が残ったか。削った量だけで効果としない。

結果が未観測なら期待と実測を区別する。既に適切な余地があれば変更を増やさず、足りないものがあれば補う。余白を作るためだけに未依頼の変更や新しい宿題を足さない。
