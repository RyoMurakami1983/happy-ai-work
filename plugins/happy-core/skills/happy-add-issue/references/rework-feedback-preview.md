# 手戻りfeedback（Preview）

実装・設計の手戻りを、次の仕事にも役立つ改善候補へつなぐ試用手順。元の仕事を直す責務は呼出し元に残し、ここではHappy AI Workへのfeedbackだけを整理する。元の仕事の完了報告、または未完了のblockerと再開点を先に渡す。調査のために元の作業を再開・拡張しない。

## 候補にするか

実際に観測した出来事があり、指示の曖昧さ、責務境界、確認観点などを変えると別の作業にも役立つ理由を短く説明できる場合だけ拾う。一度の出来事でも再利用価値があればよく、繰返し回数をノルマにしない。

通常のTDDのRED、単純な誤字、今回限りの好み・要求変更、まだ起きていない失敗だけでは候補にしない。現在の作業repo固有のバグ・具体的backlogは`github-issue`へ、Happy AI Workの軽い利用feedbackはこのskillへ分ける。どちらも無断で投稿しない。該当しなければ静かに終え、「候補なし」の報告や追加質問を増やさない。

## 具体から核へ

会話や成果物に既にある根拠を使い、次を必要十分な長さで分ける。空欄を埋めるために仮説や仕様を作らず、不明なら不明とする。

- **観測事実**: 何をし、何が期待と違い、どの修正が求められたか。修正前後の具体例と、確認できる証拠を残す。修正後が未検証ならそう記す。
- **原因仮説**: なぜ起きた可能性があるか。skillの不足、実行時の読み落とし、要求変更、環境などを証拠に照らし、利用者の内心や「深い意図」を断定しない。
- **反対仮説・不明点**: skillを変えなくても説明できる可能性、仮説を反証する事実、まだ確かめていないことを区別する。根拠のない対案を水増ししない。
- **改善候補**: 次回どの判断・確認が変わると役立つか。現行指示にも同じ対策があるか確認し、既存規約の読み落としを新しい規約の不足へ置き換えない。観測から説明できる最小の変更と、どう確かめるかを示す。skillの欠陥認定や恒久規約の追加へ飛躍しない。

`tanka-to-haiku`を読み、困りごとの具体、改善の核、必要な条件が伝わる形へ組み直す。原因の証明や詩の生成に使わず、修正前後・証拠・不確かさを短さのために捨てない。公開できない証拠は匿名化した具体例へ置き換え、匿名化で失う検証範囲も残す。秘密・内部URL・非公開ログを根拠として公開しない。

## 一候補から投稿previewへ

1. 同じ出来事と期待する改善を、現在の会話・handoffにある候補と照合する。設計・実装が両方関わっても一候補に関連skillを併記し、引継ぎ先には候補と提示済み／保留／辞退の状態を渡す。新しい永続台帳や全履歴検索は必須にしない。
2. 既存Issueを読み取り専用で検索する。重複なら既存URLと接続案を示すだけにし、新規Issueや追記コメントを自動作成しない。検索できなければ「重複未確認」のdraftに留める。
3. 新規候補は`happy-add-issue`本体の公開情報保護と投稿前previewに戻す。固定投稿先・公開範囲・title・body・実在label候補を見せ、今回の投稿確認を待つ。候補を拾う許可を投稿許可へ読み替えない。
4. 保留・辞退ならそこで止め、同じ候補を別skillや次の終了報告から再提示しない。投稿したら返されたURLを確認して一度だけ渡す。失敗・拒否・結果不明を成功とせず、結果不明なら元の作成結果を読み取り専用で確認してから次を判断し、確認できるまで投稿を重ねない。

Issue整理やこのPreview自体の試用中に受けた修正を、同じ実行内で新たなfeedback候補へ再帰させない。明示的にその改善を依頼された場合は別の依頼として扱う。Issue作成からskillの自動改変・実装開始へ進まない。

## 試用で確かめること

Issue件数ではなく、採用できる候補の質、根拠の追跡可能性、誤った原因帰属・重複・中断負担、適用後の同種手戻りを観察する。元の仕事の報告に重い評価表を足さず、実際に得た証拠と未確認を必要な範囲で残す。模擬確認を実利用効果へ読み替えず、継続・修正・撤回・拡張を利用者が判断できるようにする。
