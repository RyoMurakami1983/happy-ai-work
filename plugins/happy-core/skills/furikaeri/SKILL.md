# ふりかえり

進捗報告だけで終わらせず、次回の判断が変わる学びを残す。会話を正本とし、外部serviceへの登録や改善実装を始めない。保存や後続skillへの委譲は、候補を示してユーザーが選んだ後の別工程にする。

## YWTの意味

- **Y（やったこと）**: 実際に行ったこと。Notionの完了・進行中の「今日のタスク」は主要な材料だが、予定外作業や途中まで進めた作業も含む。未着手の予定はYにしない。
- **W（分かったこと）**: Yから得た観測、学び、判断材料。すべてをタスク化しない。
- **T（次にやること）**: Wを踏まえた実行可能な行動候補。通常の後続作業と改善候補を区別する。「気をつける」のように完了判定できない表現は具体化する。

## モード

- **Quick YWT**: 短く素直な作業。Y、W、Tを整理し、「事実か解釈か」「別の説明はないか」だけを短く確認する。
- **KPT**: 複数工程、詰まり、出戻り、再発、日次横断がある作業。Keep、Problem、Tryを整理し、観測事実、代替説明、再発性を確認する。

## ワークフロー

1. 対象期間と当初の目的を確認する。
2. 利用可能で必要ならNotionの今日ビューを材料にし、完了、進行中、予定外、未着手を区別する。Notionが使えなければ会話から確認する。
3. 実際に起きたこと、未完了、重要な判断を時系列で短く並べる。
4. 摩擦が軽ければYWT、再発や構造問題があればKPTを選ぶ。
5. WやProblemは、観測事実と解釈を分け、少なくとも一つの代替説明を検討する。Quickでは深掘りを強制しない。
6. Tを「通常の次のタスク」と「改善候補」に分ける。学びだけで行動が不要ならTを無理に作らない。
7. 明示期限や重大riskがなければ、新しい改善より進行中作業を閉じることを優先する。期限、影響、所要時間を短く比較し、優先順位を示す。
8. 複数の未着手タスクを翌日へ一括移動する場合は、進行中作業、再見積り、翌日の利用可能時間を確認する。容量を超える場合は、優先分だけを翌日に置き、残りを日付未定の「次」へ戻す案をpreviewする。
9. 通常の次のタスクは、ユーザーが登録を望む場合、利用可能なNotion操作へpreview付きで委譲する。専用skillを増やさず、`improvement-loop`へは渡さない。
10. 改善候補は通常1件、必要時でも最大3件に絞る。「その改善を進める」「登録する」「指定日に実行する」などユーザーの合意が得られた候補だけを`improvement-loop`へ渡す。候補提示や「明日何をするか」という質問だけを選択済みと見なさない。
11. file、Notion、GitHubへの保存やIssue作成は、正確な内容と宛先を示し、ユーザーの確認を得て別工程で行う。

## 出力

- 対象と達成事項
- YWTまたはKPT
- 通常の次のタスク
- 改善候補（通常1件、最大3件）と選択理由
- `improvement-loop`へ渡す候補と、今は渡さない候補
- 必要なら残存risk／未完了

秘密情報、個人data、社外公開できない案件情報は、保存・共有候補から除外または匿名化する。
