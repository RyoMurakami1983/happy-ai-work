# To PRD

会話と確認済み資料に根拠がある内容だけを、要求のsource of truthへ整理する。
PRDは「なぜ・誰の・何を・どこまで」と、目的→要件→Acceptance Criteriaの対応を所有する。合意済みの内容を正式な要求として記録し、未合意の候補をこのskillの裁量で確定しない。「どのモデルで・どの構造で・どの順に」は後工程へ渡す。

## 文脈・目的・要件・受入条件

| 概念 | 記録する内容 |
| --- | --- |
| Context（文脈） | 誰が、どのような状況で、何に困っているか。その根拠となる観察・制約 |
| Purpose（目的） | 文脈から生まれる、実現したい状態・価値。機能名や技術方式と区別する |
| Requirement（要件） | 目的を達成したと判断するために成立すべき条件 |
| Acceptance Criteria（受入条件、AC） | 要件の成立を外部から確認する条件・操作と、観測できる期待結果 |

上位目的に対し、別々の達成条件を持つ下位目的が資料にある場合は、その関係を残す。小規模変更のために目的の階層を作らない。

## 入力ゲート

PRDを書く前に、次が会話または資料に存在するか確認する。

- 誰の、どんな問題を解決するか
- 解決後に得られる成果
- 何ができたら成功か
- 今回扱わない範囲の素材

認証・認可を変更する場合は、actor × action × resource scopeのpolicy matrix、許可・拒否、tenant / organization境界、未定義roleの扱いも確認する。決まっていない項目はblocking Unknownsとして `interview-with-docs` へ戻す。

不足がある場合は、影響する目的・要件とともにUnknownsへ置く。草案化が依頼されていれば保存まで進める。進め方が未指定で不足が結論を左右する場合だけ、草案化か `interview-with-docs` での深掘りかを確認する。追加インタビューをこのskill自身で始めず、勝手に補完しない。

## 根拠の扱い

- 会話や確認済み資料にない機能、user story、判断を発明しない。
- 観察された事実、合意済みの決定、推定、未確定の候補を区別し、目的と要件から会話・資料の出典を追えるようにする。推論は「推定」と明示する。
- 決まっていないことは本文の決定事項に混ぜず、Unknownsへ置く。
- repoがある場合は、用語、既存機能、制約、ADRに接地する。アクセスできなければ「コードベース未確認」と記す。
- 会話で既に決まった技術事項は「Fixed Constraints」として記録できるが、検討案を採用済み制約に変えない。モデル分割、値オブジェクト、module、interface、DB構造、API方式、architectureをここで設計しない。

## ワークフロー

1. 文脈、問題、利用者を根拠に接地し、実現したい状態を目的として整理する。機能案しかない場合、目的を逆算して合意済み扱いにしない。
2. In Scope / Out of Scopeを分け、今回扱う目的を明確にする。会話にあるuser storyやjobは、その目的を補足する。
3. 目的ごとに「何が成立すれば達成と言えるか」を要件にする。機能一覧の転記で済ませず、各要件がどの目的に必要かを示す。根拠が不足する条件は候補またはUnknownsに留める。
4. 要件ごとに、前提・操作と期待結果をACへ具体化する。合格/不合格を判定できない「速い」「使いやすい」等は、未合意の閾値や測定条件を発明せずUnknownsへ戻す。表示変更等のACに合格しても、利用者価値そのものを実証済みとは扱わない。
5. 目的→要件→ACを照合する。今回扱う目的に必要な要件、各要件にACがあるかを確かめ、目的に結びつかない要件や不足を残さず、未解決なら明示する。複数目的・要件では `P-01` / `R-01` / `AC-01` 等のIDや対応表を使い、小規模なら一文・箇条書きでよい。既存IDは保持する。
6. 既決の制約、前提、依存、コードベース確認状況を記録する。Unknownsには影響する目的・要件、次工程を止めるか、確認先を添える。後工程から返された要件不足もここへ戻し、答えを得てから要求へ反映する。
7. 根拠とscopeを再確認し、確定済み部分と未確定部分を区別して次工程へhandoffする。

## 生成テンプレート

```markdown
# PRD: [Name]

## Context
## Problem
## Users
## Purpose
### Top-level Purpose
### Relevant Sub-purposes
## In Scope
## Out of Scope
## User Stories / Jobs
## Requirements
## Acceptance Criteria
## Fixed Constraints
## Dependencies
## Unknowns
## Source Notes
```

見出しは案件規模に応じて統合・省略してよい。目的・要件・ACの区別と対応は保ち、下位目的やuser storyの材料がなければ埋めない。既存PRDでは `Desired Outcomes` 等の見出しも活かし、意味の重複を増やさない。

複数要件を整理するときの記載例（表の形式自体は必須ではない）:

```markdown
## Requirements
| 要件 | 成立すべき条件 | 対応する目的 | 根拠 |
| --- | --- | --- | --- |
| R-01 | [条件] | P-01 | [合意・資料の箇所] |

## Acceptance Criteria
| AC | 対象要件 | 前提・操作 | 観測できる期待結果 |
| --- | --- | --- | --- |
| AC-01 | R-01 | [条件・操作] | [合否を判定できる結果] |
```

成果物は保存を既定（saved-by-default）とし、同じ案件の `NNN` を使って `docs/prd/NNN_PRD.md` へ必ず保存する。`NNN` は同案件のgrill / design / planと共有し、既存番号がなければrepo内の最大番号+1を使う。repoの `CONTEXT.md` がなければ作成し、案件で確定した用語・境界があれば更新する。

次工程へのhandoffには必ず次のいずれかを含める。保存済み成果物が1つでもある場合は、会話で補った内容だけであっても既知のpathをすべて列挙する。

```yaml
artifacts:
  - docs/prd/NNN_PRD.md
```

conversation-only は利用者が明示的に文書不要とした場合、またはsmall one-sliceで後続の判断記録が不要な場合だけ許容し、`exception reason:` を併記する。複数repo、複数slice、public contract、migration / operationsを伴う場合は選べない。

## 出荷ゲート

- 目的・要件が会話または資料に接地し、未合意の候補を正式決定にしていない。
- 今回扱う目的→要件→ACの対応を追え、不足は影響とともにUnknownsへ明示されている。
- Acceptance Criteriaが内部実装ではなく観測可能な振る舞いになっている。
- Out of Scopeが空ではない。
- 未確定事項がUnknownsに隔離されている。
- 新しいarchitecture、test seam、vertical slice、file pathをPRDで決めていない。

草案の保存は要求確定を意味しない。blocking Unknownsがある場合は草案と明記し、確認が必要な要求を次工程の確定入力にしない。

## 次工程

- handoffには目的・要件・ACの対応、合意状態、制約、blocking Unknownsを含める。実装へ渡す場合は、実装範囲、省略工程と理由、着手許可の状態と根拠となる利用者発言も添える。
- 用語やドメインの概念・境界を整理する必要がある場合は `domain-modeling`。目的・要件はPRDを参照させ、不足はPRDへ戻す。
- 構造判断が必要なら `technical-design`。
- 構造が既に固定され、複数sliceの順序だけ必要なら `implementation-plan`。
- 単一の明確な変更なら `implement` へ直接渡してよい。この経路を選ぶときは[垂直スライスと短縮条件](../implementation-plan/references/vertical-slice.md)を読み、設計書・計画書と設計レビューの省略理由を具体的に示し、その内容で実装してよいか必ず確認する。PRDへの賛意だけで着手させない。同じ範囲・省略内容で取得済みの許可は、根拠を引き継いで再質問しない。
- Unknownsが実装をブロックする間は自動着手させない。

## 注意点

- セクションを埋めるための水増しをしない。
- 追加のインタビューをしない。
- PRDをtechnical designやtask checklistの代わりにしない。
