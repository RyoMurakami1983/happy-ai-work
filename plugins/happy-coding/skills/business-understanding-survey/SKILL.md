# 業務理解アンケート

資料にある事実を再確認し、モデルやシステムの判断を左右する未知を、回答可能な質問へ変える。
質問票を作ること自体ではなく、回答後に目的・制約・選好・例外を更新できることを完了条件とする。

## 入力ゲート

着手前に次を確認する。

- 何を決めるためのアンケートか
- 回答者の役割と、回答を利用する役割
- 会話、議事録、データ分析、PRD、`CONTEXT.md`などの根拠資料
- 既に確認済みの事実、推定、矛盾、未確認事項
- 回答後に更新する成果物

根拠がない業務ルールや選択肢を発明しない。判断材料が不足している場合は、空欄を埋めず「未確認」として質問候補へ残す。

## ワークフロー

### 1. 根拠を分ける

資料から論点を抽出し、`確認済み事実`、`推定`、`矛盾`、`未確認`に分類する。各論点に根拠の場所と、回答によって変わるモデル・仕様を対応付ける。

数理最適化では少なくとも次を確認する。

- 意思決定変数: 現場が決める量、採否、順序
- ハード制約: 違反を許さない規格、能力、安全、在庫、合計条件
- ソフト制約: 逸脱を罰則付きで許せる条件
- 目的関数: 最小化／最大化する業務価値
- 優先順位と同点時の選好: 原価、種類数、作業性、在庫消化、慣行など
- 例外と人の確認: 自動採用できない条件、説明が必要な条件

### 2. 知りたい内容に回答形式を合わせる

[質問設計ガイド](references/question-design.md)の対応表を使い、論点ごとに次のいずれかを選ぶ。

- `fact_confirmation`: 現時点の理解が正しいかを、確認／修正／不明で確かめる
- `single_choice_rule`: 未決定の業務ルールを、具体的で排他的な選択肢から決める
- `tradeoff_comparison`: 一つの判断軸だけが異なる2〜3案を比較し、選択理由を得る
- `free_text_example`: 例外、失敗例、経験則、条件付き判断を具体例とともに得る

一律の「その通り／修正／分からない」を全質問へ使わない。確認したいのが具体的なルールなら具体的な選択肢、暗黙知なら自由記述を使う。

### 3. 現場の言葉へ直す

- `Target`、`MeltWeight`、`Min/Max`のような内部名を質問の主語にしない。
- `CONTEXT.md`や資料にある現場語を優先し、内部名は必要な場合だけ括弧内の対応情報にする。
- 「分母」「ペナルティ」のような実装語は、何を合計し何と比べるか、どんな不都合を避けたいかへ言い換える。
- 一つの質問では一つの判断だけを尋ね、回答の利用目的を短く添える。

### 4. 質問票を構成する

[questionnaire-template.json](assets/questionnaire-template.json)をコピーし、案件用の管理対象ファイルへ編集する。生データ領域へ作成物を置かず、repoの文書規約を優先する。

質問は原則として次の順に並べる。

1. 目的と回答方法
2. 現時点で確認できた事実の再確認
3. 業務ルールとハード制約
4. 目的、優先順位、同点時の選好
5. 例外、失敗例、暗黙知
6. 補足と回答後の扱い

JSONを使う場合は次で検査する。

```powershell
python scripts/validate_questionnaire.py path/to/questionnaire.json
```

### 5. HTMLへ展開する場合

ユーザーが画面、HTML、公開サイト、保存機能を求めた場合だけ `sites-building` を併用する。先に質問内容と回答形式を確定し、見た目より次を優先する。

- 次のページへ移ったら先頭を表示する
- ブラウザ内の下書きと、サーバーへ保存済みの回答を区別して説明する
- 保存成功後に回答番号または確認方法を示す
- 回答一覧と詳細表示は回答者用画面から分離する
- 回答者用と管理者用の認証・認可を分離し、判定をサーバー側で行う
- 合言葉や秘密情報をsource、テンプレート、Gitへ埋め込まない
- 公開範囲、保存先、保管期間、個人情報の扱いを明示する

HTMLが不要な依頼へサイト実装を広げない。ローカルで使う確認票だけならMarkdownやJSONで完了してよい。

### 6. 出荷前に検証する

- 質問文と回答形式が同じ情報を求めているか
- 選択肢が相互排他的で、回答後の仕様判断に使えるか
- 「場合による」を選べる質問には条件の記入欄があるか
- 比較案は一つの判断軸だけを変え、差と選択理由を説明できるか
- 確認済み事実と提案・推定が混ざっていないか
- 現場の利用者が内部用語なしで理解できるか
- 回答から目的関数、制約、選好、例外のどれを更新するか追跡できるか

代表例だけでなく、矛盾する資料、条件付きの回答、該当なし、分からない、自由記述が空の場合も確認する。

## 出力とhandoff

出力には次を含める。

- アンケートの目的と回答者
- 根拠と状態を持つ質問一覧
- 各質問が更新するモデル／仕様上の論点
- 回答の保存・閲覧・権限境界（実装する場合）
- 回答後に更新するartifact

回答が集まったら、用語と業務境界は `domain-modeling`、要求は `to-prd`、構造判断は `technical-design`へ渡す。アンケート回答をそのまま決定事項にせず、矛盾と未回答を残して合意を更新する。

## 境界

- 一般的な顧客満足度、従業員意識、市場調査の設問作成には使わない。
- solver、数理モデル、業務システムそのものは実装しない。
- 回答者が決められない技術事項を現場アンケートへ押し付けない。
- 機密の生データ、回答内容、認証情報をテンプレートやskillへ取り込まない。
