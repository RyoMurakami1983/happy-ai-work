description: 文書や既存repoを根拠に要件をインタビューし、用語と境界を整理する。資料を基に仕様を固めたいときに使う。

---

この skill は、資料に基づく要件インタビューと合意の記録を担い、`happy-coding` の `domain-modeling` へつなぎます。会話、指定された文書、既存repoを根拠に、実装や執筆へ渡せる合意を作ります。

## 実行ルール

1. 指定された文書とrepo内の関連資料を先に読む。外部ページが指定された場合は、利用可能なコネクタまたはブラウザで原文を確認する。
2. 既決事項・根拠・矛盾・判断を左右する未知を分け、資料で解消できず人にしか答えられないことだけを聞く。機能や問題と到達したい状態の関係が曖昧なら目的を確かめ、明瞭な合意は聞き直さない。目的・条件・選択肢を推測で確定せず、比較実装を始めない。
3. `domain-modeling` の用語整理（Vocabulary pass）で、合意した用語・定義・意味の境界を整理する。[用語集の保存条件](../domain-modeling/references/CONTEXT-FORMAT.md)に従う。業務ルールや例外の候補・未決事項は合意記録に残し、モデル境界、不変条件、状態遷移が設計を左右するときだけモデル化（Formal modeling）へ渡す。未合意の目的・要件は確定入力にせず、`to-prd`で整理する。
4. 回答のたびに決定ログを更新し、同じ質問を繰り返さない。
5. 回答待ちは確認先・再開条件と独立した許可済みの資料整理・調査を分ける。未合意事項を既成事実にせず、許可のない外部連絡・催促や実装へ広げない。
6. 依頼された深さに照らして判断に十分な根拠が揃ったら、追加質問を止め、合意事項、用語、未確定事項、次工程へのhandoffを返す。重要な未知が残る場合は、確認先・検証方法と、それまで保留する判断を明示し、確定要件として渡さない。

質問が必要で優先する観点が不明なら、先に自由記述で重視点を確かめる。通常は一問ずつ推奨と理由を添えて返答を待ち、選択肢が自然なら2〜3案と自由記述を示す。一括回答の希望を尊重し、深い検討では関連する役割・例外・失敗・暗黙の業務ルールを具体例や反例で確かめる。既知や無関係な観点の穴埋めはしない。

3件以上の質問をまとめて尋ねる場合は、質問内容をこのskillで決めてから `html-questionnaire` へ渡す。利用者が会話での回答を指定した場合は、その希望に従う。1〜2件の追加確認は会話で続けられる。HTML生成を要件合意の完了とみなさない。

## 成果物（saved-by-default）

結果を後続PRDへ根拠・未決事項・重要判断として引き継げる場合、grill結果の単独保存は不要です。それ以外は `docs/grill_results/NNN_GRILL_WITH_DOCS_RESULT.md` へ保存します。`NNN` は同案件のPRD / design / planと共有します。

conversation-only の可否と保存必須条件は、[共通成果物契約](../implement/references/WORK_ARTIFACTS.md#conversation-only-exceptions)に従う。例外を選ぶ場合は `artifacts: conversation-only` と具体的な `exception reason:` をhandoffに記載する。

文書にない内容を事実として補わない。推定は推定と明示する。質問が不要なほど要求が明確なら、grillを長引かせずhandoffを作る。

## 迷ったときの判断

- ゴールや判断軸が曖昧なら、上記のインタビューへ戻る。
- 用語や境界が曖昧なら `domain-modeling` に戻る。
- 実装判断に影響しない好みは、推奨を示して保留可能にする。
- 要求をPRDとして合意・保存するなら `to-prd`、構造判断が必要なら `technical-design` へ渡す。

## 引き継ぎの確認

合意記録とhandoffで、確認や保留を選んだ根拠、確定範囲・残る未知・再開条件を追えるかを見る。相手の理解や待ち時間の削減は、観測できた範囲でのみ述べる。
