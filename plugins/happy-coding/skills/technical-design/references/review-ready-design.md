# レビュー可能な設計の記載ガイド

複数要件・境界を扱う設計や、独立レビュアーへ引き継ぐ場合に使う。以下は記載項目の例であり、固定の書式やチェック数による合否基準ではない。既存文書への参照を使い、根拠の本文を複製しない。

## 1. Normative inputsとtrace

規範入力には出典のpath / 節または会話上の合意、IDがあればそのID、合意状態を示す。要件・AC、業務上の契約、固定済み技術制約の正本を区別する。現行挙動の証拠や推定は別に置く。

| 目的 / 要件（出典） | モデル責任 / 不変条件（該当時） | module / interface / 設計判断 | AC / 観測境界・期待結果 |
| --- | --- | --- | --- |
| [合意記録の箇所または既存ID] | [条件を守る責任と根拠] | [実現手段と担当箇所] | [操作・入力と外部から確認できる結果] |

- 対象要件ごとに実現手段と検証先を追い、対応のない要件は未解決として示す。
- 主要な構造判断からも要件・制約へ戻れるようにする。横断的な安全対策等は既存規約・外部contract・安全invariantへ根拠付けでき、架空の製品要件を作る必要はない。
- 一つの要件を複数moduleで担う場合は、保証責任と協調する境界を示す。一目的一クラスを要求しない。
- 新設予定のmoduleやinterfaceは予定と明記する。既存testがあれば実在するpathを添え、未実装の検証案を実行済みの証拠にしない。

小変更の記入例：合意が「保存ボタンの表示を『登録』へ変更し、保存動作を維持する」であれば、「表示名変更の要件 → 既存画面のボタン文言 → 表示の確認と同じ保存動作の確認」と一文で追える。モデル文書や新しいIDは不要。

## 2. Change scenariosとexpected locality

境界の選択に影響する、既知の変更または根拠のある仮説を扱う。現在観測した弊害と将来riskを混同しない。

| 変更シナリオ / 理由・根拠 | 変更予定箇所 | 影響を閉じる範囲 / 維持する挙動 | 波及・同時変更・互換性risk | 費用と判断 |
| --- | --- | --- | --- | --- |
| [何が変わるか、なぜか、確定か仮説か] | [module / interface等] | [他目的への影響を避ける境界] | [境界を越える依存と具体的な弊害] | [分割・共通化・既存構造維持の理由] |

たとえば参照用の列追加が想定されるなら、読取側の形の変更が更新時の業務条件へ波及するかを確認する。要件差や波及が小さければ既存構造を保つ判断でよい。観測していない変更頻度を数値で補わず、仮説だけを理由に汎用frameworkを導入しない。

シナリオは境界を評価する材料であり、実装対象の追加ではない。新しい要件として扱うには上流の合意が必要。材料がなければ「未確認」等と理由を示し、欄を埋めるために発明しない。

## 3. Domain invariantsとinterface contracts

業務条件の意味・正本はdomain modelまたは同等の合意記録に置く。technical designではそれをどこで、どう保証するかを決める。

| 項目 | 記載する内容 |
| --- | --- |
| 操作 / 責任境界 | 変更するpublic interface、呼出側と保証側、入力・戻り値の型や形 |
| 根拠 | 対応する要件・AC・業務ルール・既存contract |
| 不変条件 | どの対象の、どの状態・期間で成立すべきか、責任を持つmodule |
| 事前条件 | 呼び出せる入力・状態。外部入力等で破られた場合の検出責任 |
| 事後条件 | 成功後の状態、戻り値、外部から観測できる結果 |
| 失敗時の保証 | 拒否・例外・エラー値の返し方、残る状態と副作用、部分成功の有無 |
| 保証手段 | validation、型、transaction等、条件を守る技術上の判断 |
| 確認例 | 正常・境界・拒否の入力と期待結果、確認できる境界 |

不変条件を特定操作の事前条件や成功時だけの事後条件で代用しない。生成、更新、復元等の経路が関係する場合は、保証を迂回する経路がないかも確認する。外部I/Oや並行更新がある場合だけ、部分失敗・再試行・重複・整合性の保証範囲を具体化する。副作用を戻せない設計で「失敗時はすべて元通り」と約束しない。

数値上限、権限、許される状態遷移、失敗後の業務状態が未合意なら、Unknownsと影響を記して上流へ返す。エラー形式やtransaction境界等の技術判断は、その条件を満たす手段として記録する。確認例を作るために業務条件を補わない。実装するtestコード、first test、RED/GREEN commandは後工程で扱う。

## 4. Review readinessとhandoff

| 項目 | 引き継ぐ情報 |
| --- | --- |
| Design revision | 対象designのpathと版。可能なら内容hashまたは内容に対応するcommit SHA。未コミットの差分はHEADだけでは特定できないため区別する |
| Normative sources | 目的・要件・AC、該当するdomain model、規約・制約の出典と合意状態 |
| Evidence | trace、contract、change scenario、現行構造・弊害の証拠への参照 |
| Known assumptions | 仮定、根拠、誤っていた場合に変わる設計箇所 |
| Blocking unknowns | 未解決事項、影響する要件・判断、次工程を止める範囲、戻り先。なければ「なし」 |
| High-risk decisions / Review focus | 互換性、安全性、業務条件、移行等で検証してほしい具体的な判断・問い |
| Review required / Reason | yes / noと、利用者の依頼・repo規約・対象変更のriskに基づく理由 |
| Next owner / Artifacts | 独立レビュー、上流への確認、実装計画のどこへ渡すかと、実在する資料のpath |

独立レビューの要否は、複数module / repo / teamの協調、public API / schemaの互換性、migration / rollback、trust boundary、重要な業務条件、実質的なtrade-offへの影響を考慮する。単に既存の認証処理を通る等、関係するだけで全案件を必須にしない。既存module内の明確な局所変更は省略理由を短く残せる。

レビュー資料が揃うことと、レビューで承認されることは別である。設計者は自己PASSを出さず、レビューが必要なら未実施であることと引き継ぎ先を明示する。レビューskillが未導入でも、この資料を独立レビュアーへ渡せる。

未解決事項の戻り先は、根拠調査なら `interview-with-docs`、目的・要件・ACなら `to-prd`、モデルの意味・業務上の契約なら `domain-modeling`、構造・技術contractなら `technical-design`。必要なレビューが完了し、実装を左右する未知が解消した設計を `implementation-plan` へ渡す。レビュー省略時も同じ未知の条件を確認する。

レビュー後に規範入力・contract・構造判断が変わった場合は、対象版と影響するtraceを更新し、以前のレビュー結果を無条件に引き継がず再確認範囲を示す。

## Finalization contractとの関係

このガイドのcontractは、業務条件を実現する公開操作の保証を指す。[finalization-contract.md](finalization-contract.md)は、複数案や決定変更から恒久成果物へ昇格する根拠の選別を扱う。

両方が必要な場合は、同じnormative sourceとtraceを参照する。review handoffを作るだけでfinalization contractの全書式を追加せず、その適用条件に従う。非採用案や仮説を、レビュー資料を充実させるために採用済みconstraintへ混ぜない。
