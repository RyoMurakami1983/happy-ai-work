# Evidence-driven debugging

コード変更より先に、観測された挙動、期待挙動、最小刺激、環境を固定する。

## ワークフロー

1. 症状と期待値を分け、再現条件と成功条件を一文ずつ定義する。
2. 修正前のlog、trace、screenshot、test failure、入力、version等から必要最小限のbaselineを残す。秘密情報は除去する。
3. 既知良好状態、別環境、別modeと同じ刺激で比較し、変数を一つずつ変える。
4. 入力、validation、state、I/O、network、time、concurrency、rendering等の境界で、最初に期待とずれる場所を探す。
5. 仮説を一つずつ否定可能なprobeで検証する。複数の仮説を同時に修正しない。
6. 根本原因に直接効く最小修正を入れ、同じ再現scenarioと影響範囲のgateを再実行する。
7. 症状、再現条件、調べた仮説、根本原因、修正、検証結果、残存riskを引き継ぐ。

## 注意点

- baseline取得前に探索的修正を始めない。
- log追加自体でtimingや並行性が変わる可能性を考慮する。
- 認証情報、個人data、巨大artifactを証拠として無差別に保存しない。
- 診断だけを依頼された場合は修正しない。
- GitHub Actionsの失敗は、利用可能なら専用のCIデバッグworkflowを優先する。
