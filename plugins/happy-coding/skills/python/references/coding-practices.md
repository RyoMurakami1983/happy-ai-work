# Python coding practices

- 公開関数と重要な内部境界には型ヒントを付け、複雑な戻り値を曖昧にしない。
- 外部入力、I/O、時刻、環境変数と純粋ロジックを分離する。
- `except:`や握りつぶしを避け、回復できる境界で具体的な例外を扱う。
- 可変デフォルト引数を使わず、必要なら`None`から初期化する。
- path操作は特別な理由がなければ`pathlib`を検討する。
- 長寿命applicationでは`print`より既存logging方針を使う。短いCLIの標準出力契約は例外とする。
- `dataclass`、Enum、Protocol、TypedDict等は、データ境界を明確にするときに使い、型のための型を増やさない。
- import時副作用を避け、実行入口は必要に応じて`if __name__ == "__main__":`で分離する。

## GUIから使うPythonの起動費用

根拠: [Issue #56](https://github.com/RyoMurakami1983/happy-ai-work/issues/56)。重いバックエンドの要求ごとの再起動を避けるための設計・検証契約であり、単発CLIや配布形式を一律に禁止しない。

- 実装前に、代表GUI操作ごとの要求数・頻度、processの起動箇所・生存期間、重いimport／初期化を確認する。軽い入力確認や保存が、共通entrypointを通じて不要な重いライブラリを読み込まない構造にする。
- 頻繁な処理はアプリ／セッションに寿命を合わせたPython processの再利用、軽い処理だけの依存分離、または既存のfrontend／Rust側での処理を比較する。移動時も入力検証や保存の正しさを保ち、性能対策だけで業務ロジックを二重実装しない。低頻度の独立jobや単発CLIは、起動費用が用途の許容範囲なら都度起動を選べる。
- PyInstallerの[one-file起動](https://pyinstaller.org/en/stable/operating-mode.html#how-the-one-file-program-works)では一時展開が加わる。one-dirへの変更は展開費用の候補対策であり、要求ごとのPython起動・import・初期化は残る。遅延importも最初の重い処理へ待ちを移すため、測定なしで解決済みとしない。
- 常駐化するなら、所有者と終了時の子process回収、ready待ちと要求のtimeout、要求／応答の対応付けとmessage区切り、error／異常終了の通知を決める。取消・入力更新後やtimeout済みの古い応答を画面へ反映しない。処理の取消可否と、書込み済みか不明な場合の扱いを決める。stdioならprotocol出力とlogを分離する。再起動・待ち行列には上限を設け、結果不明の保存を自動再送しない。既存IPCを優先し、常駐化のためだけにnetwork server等を増やさない。

### 実配布物での確認

対象OS・build・配布形式と代表入力を固定し、初回の起動からreadyまで、最初の要求（重い機能の初回利用も含む）、起動後の繰り返し操作の応答を別々に記録する。1操作中の要求数・process起動数と、展開／import・初期化／処理／IPCのどこで待つかを確認し、操作ごとの許容時間と比較する。複数要求の待ち時間の積み重なりも見る。

常駐化した場合は、連続操作に加えて取消・入力更新後の古い応答・timeout・異常終了・アプリ終了時の回収を確認する。測定対象が開発環境だけなら配布版は未検証と報告する。文書や静的testの成功を、実アプリの速度改善や再発防止の保証へ読み替えない。
