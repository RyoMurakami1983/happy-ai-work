# ドメイン上の判断を残すADR

repoのADR規約と既存の配置を優先する。規約がなければ`docs/adr/0001-slug.md`等の連番を使い、最大番号+1で採番する。ディレクトリは最初のADRが必要になった時点で作る。

## 対象と判断条件

このskillで記録するのは、bounded context、長期的な概念の境界、業務情報・ルールの所有責任等のドメイン判断である。長期的なドメイン境界や所有責任に影響する採用判断はADRへ残す。

それ以外でも、覆す費用が大きく、理由が自明でなく、実質的なtrade-offがあった判断はADRを検討する。単なる用語追加や一時的な検討メモでは作らない。

- 対象例: 「受注時に合意した価格」と「現在の販売価格」を別概念として扱う理由と、変更責任の境界。
- 技術設計へ渡す例: event sourcing、DB製品、同期／非同期通信、共有library、deploy単位の選択。

ドメイン判断と技術判断が関係する場合は相互参照し、一方の決定から他方の採用を推定しない。

## 最小の記録

```markdown
# [判断の短いタイトル]

Status: proposed / accepted / superseded

[根拠となる目的・要件・合意の参照]
[背景、決定した境界、理由を短く記載]
[重要な影響・trade-offと、対応するモデル文書への参照]
```

採用・提案・置換済みを区別する。選択肢や却下理由は再検討に有用なら追記するが、非採用案を恒久的な禁止へ変換しない。既存の採用判断を変える場合は、過去の理由を消さず置換先と経緯を残す。
