# 用語と意味の境界の保存

既存repoの用語集と配置を優先する。`CONTEXT.md`がMission、利用者、製品境界等も持つ場合、その内容を保持して該当箇所だけ更新する。既存の用語正本がなければ、最初の用語が確定した時点で`CONTEXT.md`を作る。

## 最小の記載例

```markdown
# 注文受付

顧客からの購入依頼を受け付け、成立した注文を管理する。

## 用語

**注文（Order）**: 顧客から受け付けた購入の約束。出荷作業を指す「配送」と区別する。

**キャンセル**: 出荷前の注文の取り消し。出荷後の返品とは別概念。

## 関連するモデル

- [実在するドメインモデル文書への参照]
```

定義は通常1〜2文で、何を表し、どの目的・文脈で使うかを示す。詳細な不変条件、状態遷移、技術構造はそれぞれの正本へ置く。

- 同じ文脈の同じ概念には標準語を提案し、合意済みの語を保存する。未合意案を確定語に置き換えない。
- 別名や避ける語は、実際の混同を防ぐ場合だけ、理由と適用範囲を添える。文脈が違う語まで禁止しない。
- プロジェクト固有の意味を持つ語を記載する。一般的な技術用語の辞書にしない。
- コードの名前と用語が異なる場合、差異を記録して次工程へ渡す。用語更新だけで既存コード名を変更しない。

## 複数の文脈

`CONTEXT-MAP.md`があれば読み、対象の用語集と関係を確認する。mapがなくても、資料で別の意味・所有責任が確認できれば区別する。複数文脈が必要と判断された場合にだけ、既存構成に合わせてmapを追加・更新する。

mapには、各文脈の目的、用語集の場所、業務情報の所有者、受け渡す意味を記載する。たとえば、注文受付と請求管理で同じ「顧客」を扱っていても、購入者と請求先の違いを記録する。

業務上の関係から、共有型、HTTP、イベントバス、独立service等を自動的に決めない。それらが既決なら技術設計の正本へ参照し、未決なら`technical-design`へ渡す。
