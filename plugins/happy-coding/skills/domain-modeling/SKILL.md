# ドメインモデリング

合意済みの目的・要件を、業務の言葉で責任を説明できるモデルへ落とす。現実のモノの写しではなく、目的に必要な概念・data・振る舞いのまとまりとして扱う。

## 境界と深さ

目的・要件・ACの正本はPRD等の合意記録。本skillで新設・変更・確定しない。意味・責任の境界、業務ルール、操作前後の条件を扱い、module、public interface型／signature、DB・通信方式、実装順は決めない。要件の穴を問う反例は作れるが、未合意の答えを確定条件にせず上流へ返す。一般的な「覚えておいて」や技術ADR記録だけでは起動しない。

呼称・意味・文脈だけの**用語整理**は既存用語集／`CONTEXT.md`で完了し、PRDや空のモデル文書を要求しない。`interview-with-docs`経由でも同じ。境界・ルール・不変条件・遷移が設計を左右する**モデル化**ではモデル文書と用語集への参照を作る。単純CRUDへ状態機械や分割を一律追加しない。

## 接地と用語

repo規約、既存用語集、`CONTEXT.md`、存在すれば`CONTEXT-MAP.md`、関連ADR・モデル文書を読む。map有無だけで文脈数を断定しない。モデル化では目的・要件・ACと合意状態を確認し、既存IDを保持する（小規模なら根拠箇所参照でよい）。読めるコード・testと用語／振る舞いを照合し、コードを要求の正しさの証明にせず、未確認を明記する。確定／モデル案／現行挙動／Unknownsを分け、上流不足でも根拠ある部分は整理し、未決依存部は草案とする。

同語異義と同義異語を探し、目的・文脈に合う具体名、短い定義、他概念との差を提案する。文脈の異なる同名概念を無理に統一しない。資料・合意で解けない差だけ具体例で確認し、コードとの不一致を示して黙って正本を選ばない。[CONTEXT-FORMAT.md](references/CONTEXT-FORMAT.md)に従い確定語・意味境界を既存正本へ反映する。一括rename／実装変更は行わず、対応箇所・差異を引き継ぐ。

## モデルと業務契約

モデル化時だけ[DOMAIN-MODEL-FORMAT.md](references/DOMAIN-MODEL-FORMAT.md)を読み、必要な深さで次を整理する。

- 各モデルの目的・要件、必要概念・data・振る舞いを対応付け、要件の言い換えだけにしない。同じ理由で変わる条件をまとめ、異なる目的の変更が干渉する所を境界候補とする。見た目の重複だけで共通化しない。
- 具体的な変更scenario／不整合を減らす場合に分割する。一目的一クラス、全名詞entity化、bounded context毎のservice化を前提にしない。
- 更新の正しさ、参照情報、保存／復元制約を区別する。別DTO／table／service化は要件差を根拠に`technical-design`で決める。
- ルールの根拠と責任モデル、またがる条件の関連モデルと業務責任境界を示す。不変条件にはモデル・成立する状態／期間を付け、操作の事前／成功後の事後条件と区別する。
- 状態が論点なら許可遷移・条件・成功結果・拒否時状態を整理し、未定義遷移を推測で許可／拒否しない。操作の入力・必要状態・成功条件・失敗時に守る条件を示し、例外型／戻り値形式は技術設計へ渡す。
- 正常・境界・拒否、必要なら変更scenarioで照合する。例のために未合意の上限・権限・例外を決めない。

不足は根拠要件・具体例・未決問・影響モデル・次工程を止めるか・戻り先を添える。目的／条件／scope／AC不足・変更は`to-prd`、業務事実調査・関係者深掘りは`interview-with-docs`へ返す。実装で発見した条件も同経路とし、コード制限を新業務ルールへ黙って追加しない。blocking不足のモデルを確定入力にせず、非影響部と未決部を分ける。

## 保存とhandoff

`CONTEXT.md`は簡潔な用語・意味境界に留め、既存Mission等を削除・再編せず詳細ルール／技術設計を詰め込まない。モデルは既存正本へ反映し、なければ`docs/domain/NNN_DOMAIN_MODEL.md`へ保存する。同案件のPRD／designと番号を共有し、新規は既存番号を調べて採番する。保存例外は共通の[Work Artifacts](../implement/references/WORK_ARTIFACTS.md#conversation-only-exceptions)に従う。低riskで後続handoff・判断記録が不要な場合は会話で返せるが、長期的な境界・所有責任やpublic contract等の保存必須条件を文書不要指定だけで省略しない。競合時はその点だけ確認し、例外時は`artifacts: conversation-only`と具体的な`exception reason:`を示す。

長期的なドメイン境界・業務所有責任はrepo ADR規約と[ADR-FORMAT.md](references/ADR-FORMAT.md)で理由を残す。技術のlong-lived structure／compatibility／migration／operationsに影響する判断はADRを省略せず`technical-design`へ渡す。

handoffに実在path、目的・要件→モデル→条件の対応、確定／提案、コード差異、未決と戻り先を含め、残る構造判断を`technical-design`へ渡す。完了前に文脈内の用語一貫性、合意根拠への追跡、正常・境界・拒否例の無矛盾、要件／技術の無断確定や未決混入がないことを確認する。
