# ドメインモデリング

目的・要件を守る責任を、業務の言葉で説明できるモデルへ落とす。モデルは現実の「モノ」の写しではなく、特定の目的に必要な概念・データ・振る舞いのまとまりとして扱う。

## 役割の境界

- 目的・要件・Acceptance Criteriaの正本はPRDまたは同等の合意記録。このskillで製品要件を新設・変更・確定しない。
- モデルの責任、意味の境界、業務ルールと操作前後の条件を扱う。module、public interfaceの型・signature、DB方式、通信方式、実装順序は決めない。
- 要件の穴を発見する問いや反例は作れる。答えが未合意なら、モデルの確定条件にせず上流へ返す。
- 一般的な「覚えておいて」や技術ADRの記録だけでは起動しない。ドメインの用語・モデルに関係する依頼かを確認する。

## 処理の深さを選ぶ

| レベル | 選ぶ場面 | 成果物 |
| --- | --- | --- |
| 用語整理（Vocabulary pass） | 呼び名、意味、適用する文脈だけを整理する | 既存の用語集／`CONTEXT.md` |
| モデル化（Formal modeling） | モデル境界、業務ルール、不変条件、状態遷移が設計を左右する | ドメインモデル文書と用語集への参照 |

用語整理だけならPRDや正式なモデル文書を要求しない。`interview-with-docs`等から呼ばれても、依頼内容が用語整理ならそこで終える。単純なCRUDへ状態機械やモデル分割を一律に追加しない。

## 入力を接地する

- 対象repoの規約、既存の用語集、`CONTEXT.md`、存在すれば`CONTEXT-MAP.md`、関連ADRとモデル文書を読む。mapの有無だけで文脈の数を断定しない。
- モデル化では、対象の目的・要件・ACと合意状態を確認する。既存IDを保持し、小規模なら根拠の箇所への参照でよい。
- 関連コードやtestを読める場合は、現在の用語・振る舞いと照合する。コードは現状の証拠であり、要求の正しさの証明ではない。未確認なら明記する。
- 確定事項、モデル案、現行挙動、Unknownsを分ける。上流が不足していても根拠のある用語やモデル部分は整理できるが、未決事項に依存する部分は草案に留める。

## 用語を整える

1. 同じ語が違う意味に使われている箇所と、同じ意味を違う語で呼ぶ箇所を探す。
2. 目的と文脈に合う具体的な名前、短い定義、別概念との違いを提案する。異なる文脈の同名概念を無理に統一しない。
3. 資料や合意で解決できない意味の差だけ、具体例を添えて確認する。既存コードとの食い違いも示し、どちらかを黙って正としない。
4. 確定した用語・意味の境界を既存の正本へ反映する。詳細は[CONTEXT-FORMAT.md](references/CONTEXT-FORMAT.md)を読む。

コードの一括renameや実装変更はこのskillの成果物に含めない。対応箇所と差異を次工程へ渡す。

## モデルと業務上の契約を作る

モデル化する場合だけ、[DOMAIN-MODEL-FORMAT.md](references/DOMAIN-MODEL-FORMAT.md)を読み、次を必要な深さで整理する。

### 目的・要件とモデルの対応

- 各モデルがどの目的・要件のために存在するか、必要な概念・データ・振る舞いを示す。要件をモデル名に置き換えるだけで済ませない。
- 同じ理由で変わる条件をまとめ、異なる目的による変更が干渉する箇所を境界候補にする。見た目の重複だけで共通化しない。
- 分割は、具体的な変更シナリオや不整合を減らせる場合に選ぶ。一目的一クラス、全名詞のentity化、bounded contextごとのservice化を前提にしない。
- 更新時に守る正しさ、参照時に必要な情報、保存・復元の制約は区別する。別DTO・table・serviceへ分けるかは、要件差を根拠に`technical-design`で判断する。

### ルール・状態・操作

- 業務ルールの根拠と、それを守る責任を持つモデルを示す。モデルをまたぐ条件は関係するモデルと業務上の責任境界を明記する。
- 不変条件は「どのモデルの、どの状態・期間で成立すべきか」を明記する。特定操作の事前条件や成功後の事後条件と混同しない。
- 状態が論点なら、許される遷移、条件、成功後の結果、拒否時の状態を整理する。未定義の遷移を推測で許可・拒否しない。
- 業務操作ごとに必要な入力・状態、成功後の条件、失敗時に守る条件を示す。例外型や戻り値の形式等は技術設計へ渡す。
- 正常例、境界値、拒否例、必要なら変更シナリオで条件を照合する。例を作るために未合意の上限値・権限・例外を決めない。

### 要件不足を返す

不足には、根拠となる要件、発見した具体例、未決の問い、影響するモデル、次工程を止めるか、戻り先を添える。

- 目的・条件・scope・ACの不足や変更は`to-prd`へ返す。
- 業務事実の調査や関係者との深掘りが必要なら`interview-with-docs`へ返す。
- 実装で見つかった条件も同じ経路で検討する。既存コードの制限を、新しい業務ルールとして黙って追加しない。

blockingな不足があるモデルは確定入力として渡さない。影響を受けない部分と未決部分を分けて引き継ぐ。

## 保存と引き継ぎ

- `CONTEXT.md`には簡潔な用語・意味の境界を置く。既存のMission等を削除・再編せず、詳細ルールや技術設計を詰め込まない。
- モデル化の成果物は既存のドメイン文書へ反映する。正本がなければ`docs/domain/NNN_DOMAIN_MODEL.md`へ保存し、同案件のPRD / design等の番号を共有する。新規なら既存案件番号を確認して採番する。
- 軽い用語整理で空のモデル文書を作らない。明示的に文書不要なら会話で同じ情報を返し、保存していないことを示す。
- 長期的なドメイン境界や業務上の所有責任の判断は、repoのADR規約に従って理由を残す。[ADR-FORMAT.md](references/ADR-FORMAT.md)を参照する。技術上のlong-lived structure、compatibility、migration、operationsに影響する判断は、ADRの記録を省略せず`technical-design`へ引き継ぐ。
- handoffには、実在する成果物path、目的・要件→モデル→条件の対応、確定／提案の状態、コードとの差異、未決事項と戻り先を含める。構造判断が残る場合は`technical-design`へ渡す。

完了前に、用語が文脈内で一貫していること、モデルの条件を合意済み根拠へ辿れること、正常・境界・拒否の例で矛盾がないことを確認する。要件や技術選定の無断確定、未決条件の確定事項への混入がないことも確認する。
