# Deep Review

固定agentファイルに依存しない。subagentが利用可能なら、差分と最小要件だけを渡して独立レビューを依頼する。利用できなければ新しい観点でローカル差分を読み直す。Copilot CLIはユーザー明示時だけ実験的に追加し、結果をコード・testで再検証する。

変更前の準備・正本・非破壊性・配布経路の確認、および複数案／決定変更後にAGENTS.md・SKILL.md・reference・README・実装・test等の恒久成果物を変更した場合は[preflight.md](references/preflight.md)を読み、instruction finalizationを独立確認する。module境界・結合構造自体が主題なら[modularity.md](references/modularity.md)を読む。

## コアをレビューの判断に使う

利用可能な`happy-core`の該当skill本文を、次の判断が必要なときに読む。全軸を一律に適用せず、本文を複製しない。

- **目的への到達**: `mokuteki-to-michi`（目的と道）に沿い、合意した目的・ACと差分を照合する。局所的な修正やtest成功だけで、必要な成果へ届くとみなさない。別の目的や未合意の要件をレビューで追加しない。
- **指摘の確かさ**: `toi-to-mikiwame`（問いと見極め）に沿い、判断を変える未知、根拠、反例を確かめる。違和感は調査の入口であり、不具合の証拠ではない。根拠が足りない候補は確定指摘とせず、重要なら未確認事項へ分ける。
- **過不足と変更の余地**: 構造の詰め込みや削りすぎが論点なら`yohaku`（余白）を参照する。理解・変更・検証を妨げる具体的影響を調べ、単なる短さや好みで抽象化・機能の追加削除を求めない。
- **完了と回復の確かさ**: 応答・保存・中断・再試行が関わるなら`kime-zanshin`（極めと残心）を参照し、相手が使う場所での結果と失敗後の状態をcontract・証拠に照らす。静的な論証と実動作確認を区別する。
- **次の判断へ届く報告**: `tanka-to-haiku`（短歌と俳句）に沿い、重要な問題と発生条件・影響・根拠が埋もれない形へ整える。確認待ちがある場合は`sennosen-to-gonosen`（先の先と後の先）を参照し、待つ部分と独立して確認できる範囲、再開条件を分ける。短縮で必要な証拠を落とさず、先回りの修正や外部連絡はしない。

参照できない場合は既存のレビュー手順で進め、未参照を報告へ短く残す。コアの名称や参照の有無だけを合否基準にせず、適用先の規約・合意済み要件・安全境界に接地して評価する。

## レビュー手順

1. diff、要件、test結果、repo instructionsを確認する。
2. 変更に応じ、正しさ・回帰・data損失・権限／機密・並行性・エラー処理・test妥当性・責務境界を調べる。
3. 各候補の行・発生条件・影響を確認し、再現／論証が弱い指摘を除く。
4. 重要度順に、場所・問題・発生条件・最小修正方針を返す。
5. なければ「重大な指摘なし」とする。

指摘の有無にかかわらず、確認範囲・未確認事項・残存riskを短く示す。コアを使った判断も別の採点表にせず、過程は調べた根拠と保留理由、結果は確認できた影響と未確認の境界として報告へ結び付ける。「重大な指摘なし」は未検証の動作保証やマージ承認ではない。

レビュー中は変更しない。修正まで依頼された場合だけ指摘確定後の別工程で実装する。スタイルの好みを不具合にしない。
