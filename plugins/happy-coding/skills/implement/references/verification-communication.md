# 検証の開始前通知と終了報告

Refs #44 / #45。検証commandを実行する前に、repoのtest分類・script・計画から、全件suiteに長い試験が含まれるか確認する。計画なしのバグ修正でも同じ扱いにする。

長い検証、負荷・耐久試験、実環境や外部資源を使う検証は、実行ツール直前の利用者向け通知に、目的・規模、区分（合成入力／一時fixture／実環境）、外部接続の有無・接続先、見込み時間とtimeout／試行budgetを短く含める。計画やツールのjustificationに書いただけで通知済みとしない。未計測なら見込みの根拠を添え、不明な時間・接続条件は不明とする。全件suiteの長時間部分も省かない。

検証の対象・変更する資源・外部接続・負荷・必要な権限・復元方法を、依頼と既存の合意から定める。不足する許可だけをまとめて確認し、合意した範囲の実行と必要な再検証は自動で進める。個々のtestや同じ範囲の再試行で許可を聞き直さない。管理者権限が必要なら対象操作と影響を限定し、通常権限で足りる工程まで昇格しない。利用者の合意とOS・実行基盤の承認は区別し、拒否を迂回しない。

通知は承認要求ではない。まとまった検証の開始時に伝え、同じ条件の各commandで繰り返さない。新しい課金、認証変更、許可を超える負荷・本番操作などが必要なときだけ、その影響と必要な判断を示して該当操作を保留する。進捗は意味のある変化を中心に短く伝える。

性能は対象projectで合意した環境・代表操作・遅延の基準で判定する。利用中のPCで試験する場合は通常操作を妨げない並列数・負荷に抑え、停止や大きな遅延を観測したら負荷を下げるか試験を止める。環境、操作、データ量、観測した遅延、未確認範囲を残し、機能testの成功を快適さの証明にしない。

終了時は利用者の優先順で主要関心ごとの対応済み・未対応・残る条件を短く伝え、検証結果はその根拠として添える。成果物が関係する場合は設定更新・生成・配置・起動確認を混同しない。合成testの成功を実環境の成功へ広げず、未実行・失敗・timeoutを区別する。詳細logはhandoffへ分け、次の判断・行動がある場合だけ示す。完了済みで判断事項がなければ追加質問をしない。
