# Runtime Evidence

実装後は対象appを通常の起動経路で開き、変更した期待に関わる代表操作を主要フローで確認する。既存設計の「予測する操作・結果 → 採用する動き → 確認方法」を再利用し、静的markup、build成功、内部値、unit test、screenshotだけで操作感を確認済みにしない。

確認する内容は変更範囲に合わせて選ぶ。

- 初期状態と主要controlが表示され、keyboard focusで到達できる。
- primary commandを実行し、activeからsuccessまたはerrorまでの表示が内部結果と一致する。
- errorまたはdestructive operationでは、利用者の意図を保持した復帰または確認がある。
- 最小viewportまたは指定された拡大率で、主タスクに必要な情報と操作が利用できる。
- メンタルモデルに関わる変更は、対象環境の選択と開く操作の区別、拡大時の注目位置、移動方向など、変更した予測と実際の表示・feedbackを連続操作で照合する。例えば写真ビューアの選択・拡大・移動をまとめて変更した場合、一つのボタン操作だけで全変更を確認済みにしない。

記録には対象OS・入力機器、起動方法、操作、期待結果、観測結果、未確認の状態を含める。証拠の範囲を次のように区別する。

- **自動runtime確認**: UI自動操作で観測した選択・状態遷移・feedback。合成touchイベントや内部値の検査を、実機gestureの操作感へ広げない。
- **実機の物理入力**: 対象機器でのピンチ・2本指パンなどを実際に入力し、注目位置の保持、両軸の移動、競合や復帰を確認した範囲。
- **利用者本人の受け入れ**: 利用者が予測どおり理解・操作できるかを本人が評価した範囲。前二者の成功で代替しない。

物理入力や本人評価ができなければ、その範囲を未確認として残す。全変更へ実機試験や一律承認を追加せず、既存のacceptance / HITL契約に従って残る判断と次の確認を示す。失敗時は再現条件と画面証拠を残し、実装または設計へ戻す。
