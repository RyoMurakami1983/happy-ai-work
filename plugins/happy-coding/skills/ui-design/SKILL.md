# UI Design

見栄えではなく、利用者が主要タスクを安全に理解・実行・復帰できるUIを設計する。CSSやfrontend実装は担当せず、実装契約が必要なら適切な実装skillへ渡す。

## 入力と適用範囲

対象の利用者、主目的、主要フロー、制約を確認する。現状UIの批評には実画面、スクリーンショット、実装のいずれかを用い、再設計には既知の要求と対象画面を用いる。これらがなく設計判断をできない場合は、必要最小限を質問する。

- PRD全体の策定は `to-prd`、技術構造の設計は `technical-design`、UI実装は対象stackのskillへ渡す。
- ロゴ、イラスト、ブランド制作だけが目的の場合は適用しない。
- 現在のUIを診断または再設計するときは [design-principles.md](references/design-principles.md) と [review-checklist.md](references/review-checklist.md) を読む。
- 実装後の確認では [runtime-evidence.md](references/runtime-evidence.md) を読む。

## 設計フロー

1. 利用者、主目的、成功条件、主要タスクフローを明確にする。
2. empty、idle、active、success、error、権限不足、読み込み中など、対象フローに必要なUI状態と遷移を列挙する。
3. 近接・整列・反復・対比を、情報のまとまり、優先度、読順、操作の区別として診断する。
4. affordance（操作可能な性質）と signifier（それを伝える手掛かり）を分け、操作結果とfeedbackが利用者の予測に一致するか確認する。
5. commandを primary、secondary、destructive に階層化し、頻度と誤操作時の影響に合わせて配置と確認を決める。
6. keyboard、focus、label、色以外の状態伝達、最小viewportを含むアクセシビリティ条件を定める。
7. 実装対象と対象外、画面ごとの変更案、検証条件を明確にしてhandoffする。
8. 実装後は少なくとも一つの主要操作を実画面で行い、状態遷移とfeedbackを検証する。

## 不変条件

- 存在しない機能を操作可能に見せず、表示状態を内部状態と矛盾させない。
- 自動fallbackで利用者の意図を変更しない。危険操作は頻度と影響に応じて二次配置または確認を使う。
- 色だけに状態を依存せず、可視の操作はキーボードで到達・実行可能にする。
- 個別プロジェクトの色、余白、CSS値を普遍原則として持ち込まない。

## 出力

次を、必要な粒度で実装担当者が利用できる形にする。

- 現状評価（重大度、根拠、利用者への影響）
- 主要タスクフローとUI状態表
- command hierarchy、レイアウト方針、アクセシビリティ条件
- 実装対象／対象外、runtime verification、未確定事項

レビュー時は観測事実と提案を区別する。根拠のない全面再設計、好みだけの装飾提案、未確認機能の追加をしない。
