# Agent Team

「$happy-preview:agent-team でこの課題を進めて」のように、編成ごと実装を任されたときに使う。相談や計画だけを依頼された場合は、その段階に合う配役と判断理由を返す。

## 配役を決める

- 既定は利用可能な最新のSolの指揮役と作業役1体。利用者のモデル・推論量の指定を優先する。現在の担当が指揮役の指定に合えばそのまま指揮し、異なる場合は選んだ指揮役に委譲する。
- 指揮役は、利用できるLuna・Terra・Sol・Astraの各系列の最新版から、担当の複雑さ、必要なツール、失敗時の影響と検証手段に見合うモデルを選ぶ。そのモデルが対応する推論量も担当ごとに選び、新しいコンテキストを起動するときに指定する。範囲が明確な軽作業はLuna、画面の読み取りや操作が中心ならTerra、複数工程の実装・統合はSol、原因を絞りにくい障害や検証が難しい独立レビューはSolやAstraを候補にする。根拠が弱い判断や検証しにくい失敗経路には、必要に応じて推論量を上げる。
- Astraを起動する直前に利用者へ知らせる。
- 選んだモデルや推論量が使えない場合は、利用可能な候補から選び直して実際の構成と差を伝える。必要な独立確認を実施できない場合は未確認の範囲を示す。
- 指揮役は目的、受け入れ条件、触れてよい範囲、利用できる検証手段を作業役に渡す。成果を別々に検証でき、編集箇所や意思決定が競合しない案件が複数あるときは、担当範囲を分けて並列化する。共通仕様が未確定なら先に決める。
- **通常案件**では作業役が初版を実装し、指揮役が受け入れ結果を確認する。独立した確認が必要なら、実装者とは別の新しいレビュアーに批判的レビューを任せる。初版が合格し、確認したい具体的な懸念も残っていなければ完了できる。
- **難問**では、まず失敗を再現する。原因が特定できれば修正役が対応する。原因を絞れない、あるいは保存・復旧や非同期処理の順序などで別の視点が採否を左右する場合は、実装者とは別の新しいレビュアーに批判的レビューを任せ、修正役が対応する。タイムアウトなら同じ入力・制限で再実行し、必要に応じて時間上限だけを変えた診断結果も区別して扱う。

## 資料を読む範囲を決める

- 指揮役はまず依頼、PRD、資料一覧（何があり、何に使うか）を読む。詳細資料は、作業役ごとに担当範囲と参照する箇所を指定して渡す。
- 作業役は担当範囲の原資料を読み、判断に影響する事実・矛盾・未確認点を、シート名とセル範囲、議事録の節などの参照箇所とともに返す。
- 資料が食い違う、根拠が弱い、または重要な判断がその記述に依存する場合は、指揮役が原資料の該当箇所を直接確認する。独立レビューを行う場合は、レビュアーも採否を左右する根拠を原資料と照合する。

## 指摘を修正につなぐ

レビュアーには課題、初版の差分、受け入れ条件、再現手順、実行環境、失敗ログを渡す。要求に対する反例を探し、どの入力・操作順序で何が起き、何を期待するのかを報告させる。実行できたことと静的な推測を区別する。

修正役は指摘が要求に合うか確認し、可能なら初版で失敗する最小のテストを作る。同じ条件で修正後に通ることと、初版で通っていた受け入れ条件を維持したことを確認する。再現できない指摘や仕様が曖昧な点は、採用を左右する根拠を記録する。指揮役は複数の変更を統合した最終状態で判定する。

受け入れ結果、採用・保留した重要な指摘と残課題を短く報告する。効率の比較を依頼された場合は、観測できた手戻り込みの消費・時間・合格件数を示し、費用の試算や並列時の経過時間には集計範囲を添える。
