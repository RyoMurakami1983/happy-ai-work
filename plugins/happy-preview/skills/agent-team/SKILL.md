# Agent Team

「$happy-preview:agent-team でこの課題を進めて」のように、編成ごと実装を任されたときに使う。相談や計画だけを依頼された場合は、その段階に合う配役と判断理由を返す。

## 配役を決める

- 既定はGPT-6.2 Solの指揮役と作業役1体。全担当の推論量はmedium。ユーザー指定を優先する。現在の担当が指定の指揮役ならそのまま指揮し、異なる場合はSolに指揮を委譲する。モデルを指定する際は新しいコンテキストで担当を起動する。指定モデルや委譲機能が使えない場合は、実際に使える構成と差を伝える。
- 指揮役は目的、受け入れ条件、触れてよい範囲、利用できる検証手段を作業役に渡す。成果を別々に検証でき、編集箇所や意思決定が競合しない案件が複数あるときは、担当範囲を分けて並列化する。共通仕様が未確定なら先に決める。
- **通常案件**ではSol作業役が初版を実装し、指揮役が受け入れ結果を確認する。独立した確認が必要なら新しいSolに批判的レビューを任せる。初版が合格し、確認したい具体的な懸念も残っていなければ完了できる。
- **難問**では、まず失敗を再現する。原因が特定できればSolが修正する。原因を絞れない、あるいは保存・復旧や非同期処理の順序などで別の視点が採否を左右する場合は、新しいGPT-6.2 Astraに批判的レビューを任せ、修正をSolが担当する。タイムアウトなら同じ入力・制限で再実行し、必要に応じて時間上限だけを変えた診断結果も区別して扱う。

## 指摘を修正につなぐ

レビュアーには課題、初版の差分、受け入れ条件、再現手順、実行環境、失敗ログを渡す。要求に対する反例を探し、どの入力・操作順序で何が起き、何を期待するのかを報告させる。実行できたことと静的な推測を区別する。

修正役は指摘が要求に合うか確認し、可能なら初版で失敗する最小のテストを作る。同じ条件で修正後に通ることと、初版で通っていた受け入れ条件を維持したことを確認する。再現できない指摘や仕様が曖昧な点は、採用を左右する根拠を記録する。指揮役は複数の変更を統合した最終状態で判定する。

配役、受け入れ結果、採用・保留した重要な指摘と残課題を短く報告する。効率の比較を依頼された場合は、観測できた手戻り込みの消費・時間・合格件数を示し、費用の試算や並列時の経過時間には集計範囲を添える。
