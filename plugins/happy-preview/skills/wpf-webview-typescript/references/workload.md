# 負荷と検証

## データと画像

表示範囲から画像を要求し、プレビューを背景のサムネイルより優先する。画像の遅延取得とDOMの仮想化は別問題。件数と計測に応じてページングや仮想化を選ぶ。

キャッシュは件数とbyte数で制限する。pending、重複検出履歴、イベント購読にも期限や解放点を置く。具体的な予算は画像寸法、メモリ、対象端末から決める。

キャンセルはUIのAbortSignalからhostのCancellationTokenへ伝える。同期decoderなど中断できない区間は、開始前・終了後・反映前に確認する。「応答を捨てた」と「処理を中断した」を区別する。

更新がないときの全件走査やJSON生成にも費用がかかる。revision、変更通知、差分送信を候補にし、実測と複雑さで選ぶ。送信後の比較だけでは生成費用を消せない。

## 変更に合う検証

| 変更 | 観測すること |
|---|---|
| bridge | 不正origin/payload、未知command、遅着・重複応答、切断時のpending解放 |
| 長時間操作 | キャンセル競合、二重実行、終了途中、完了不明からの状態照会 |
| 画像一覧 | 大量件数、素早い画面切替、preview優先、キューとメモリの収束 |
| UI移行 | 条件と選択の引継ぎ、末尾の写真送り、キーボードfocus、Esc、空状態 |
| 配布 | 実際のbundle読込み、Runtime不足時、対象CPUでの起動と主要操作 |

既存テストを尊重し、今回触れた境界に絞って追加する。bridge断片のmockだけでは、配布JSの構文エラーやホスト設定の誤りを検出できない。bundle全体の実行と実WebView2の確認を分けて記録する。

## 性能調査

入力受付、bridge待ち、C#処理、画像decode、UI更新、表示間隔を分けて測る。平均fpsだけで停止を判断しない。画面表示の間隔は、アプリ処理時間や物理的な表示遅延と同じではない。

診断は任意で有効化し、件数を制限する。ファイル名、画像本体、秘密値を記録せず、計測の負荷も確認する。UI Automationなど観測側の活動も記録し、比較条件を揃える。計測の都合でアクセシビリティを無効にしない。

## 利用者の負担を確かめる

- 入力時刻、最初の有意味な反応、完了を記録する。1秒以上の遅延は発生条件と頻度を残し、単なるspinner表示を性能改善の証拠にしない。
- 条件と編集内容を入力し、処理を取消して再度始める。値が残り、取消した処理の遅着応答が新しい入力を上書きしないことを確かめる。
- 合成データで保存の前・確定後の応答前・途中処理中に切断する。保存済み結果の照会と未完了部分の再開を確認し、欠落・二重保存・再入力がないことを確かめる。
- bridge切断、WebView reload、host終了を区別する。対応を約束した障害ごとに、メモリ外への保存と再開を確認する。

自動保存は業務操作の自動確定と分ける。draftやjournalの保存場所、寿命、秘密情報の除外を決め、書込み失敗を黙って成功扱いしない。再開地点はC#側の確定状態に基づけ、UIが記憶した進捗率だけで決めない。
