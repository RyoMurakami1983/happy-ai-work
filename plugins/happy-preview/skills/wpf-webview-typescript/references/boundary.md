# 境界と寿命

## 配信と権限

ローカル静的UIならvirtual host mappingを候補にする。公開するのは配布用assetsだけとし、利用者フォルダを丸ごと公開しない。

受信元はscheme・host・portを含む許可originで検証する。必要ならpathも制限する。遷移後の送信先も確認する。開発サーバーと製品版の許可先を分け、開発用の例外を製品版へ持ち込まない。

外部遷移、新規ウィンドウ、権限要求は用途に応じて明示的に扱う。host objectsなど不要な能力を無効にし、CSPを配布形態に合わせる。表示不具合の対処にSmartScreenなどの保護を解除しない。

JSON serializerとPostWebMessageAsJsonを使い、入力をJavaScript文字列へ連結しない。画像やファイルはhost管理のIDで参照し、要求時点の対象と権限をC#側で再確認する。IDやoriginは、それだけで認可にはならない。

## 通信契約

commandごとのpayloadと応答を定義する。discriminated union等を使えるが、型生成だけでは実行時検証にならない。未知のversion/command、サイズ超過、不正値は明確に拒否する。

応答idはpending要求と照合する。イベントは応答と区別し、重複・順序逆転に対する方針を持つ。エラーはUIが扱えるcodeと必要な説明に分け、内部パスやスタックを不用意に返さない。

一度の書込みには一つのoperation IDを割り当てる。通信タイムアウトと操作失敗は同じではない。長時間操作は受付と進捗・結果を分けることを検討し、再接続時は状態照会を優先する。再試行するなら重複実行を防ぐ保存側の仕組みまで決める。

## 非同期と終了

WebView2操作はUI STAスレッドで行う。event callbackの中で同期modal dialogやnested message loopを始めない。callback終了後にdispatcherへ渡す。deferral対応eventは必要時に取得し、例外時も完了させる。

重い処理だけを、依存APIのthread制約を確認して移す。C#のasyncはUIスレッド解放の保証ではない。

終了時は、新規要求を止め、進行中の処理へキャンセルを通知し、handler/timerを解除して所有するWebViewを解放する。UI側はpending要求を終了理由付きで解決または拒否する。終了待ちとファイル保存の整合性を先に決める。

画面世代と要求idを照合し、古い応答で新しい画面を上書きしない。キャンセルは操作IDに結び付け、前の操作の取消しが次の操作へ届かないようにする。

## 通常起動と保存先

検証用hostと通常起動で結果が違うときは、実行ファイル、起動引数、package identity、実際に参照する設定・管理記録を比べる。同じAppData文字列でも実行環境によって参照先が異なる場合がある。パス文字列の一致だけで同じ保存状態と判断しない。

再インストールや記録の置換より先に、配布物の整合性と通常起動を確かめる。記録ごとの履歴を保ち、修復が依頼された範囲でバックアップと既存の再接続APIを使う。別環境の管理記録を丸ごと上書きしない。
