# Linux Deploy

試用版。実デプロイでの効果は未検証。試用では、パス・権限の確認漏れ、利用者による修正再実行、失敗からの復旧に要した手戻りを記録する。

環境やパスを推測して適用せず、正しいデータを正しい権限で扱えることと、失敗後に人が調査・再実行できることを完了条件にする。

## 対象を実測する

- 既存の依頼から対象ホスト、アプリ、配布物、参照元、保存先、公開範囲、許容停止時間を拾う。判断を変える不足だけを確認する。既存の方式を尊重し、新規で方式未指定なら単一ホストのComposeを候補にする。
- 対象ホストでOS・ユーザーランドのアーキテクチャ・ツールのバージョン・既存サービス・ポート・空き容量を確認する。ローカル端末の結果をリモートの証拠にしない。SSH接続先の名前だけでOSや用途を決めない。
- 参照元と保存先は、利用者が意図する範囲と実在するパスを対応づける。表示名を階層へ分解しない。symlinkの解決先、所有者、親ディレクトリの通過権限も必要な範囲で確認する。共有利用時は[shared-storage.md](references/shared-storage.md)を読む。
- 必要な外部接続は対象ホスト／アプリの実行環境から確認する。認証済みAPI操作は依頼の範囲内の読取で試し、レスポンス本文や認証値を診断ログへ流さない。

## 適用と検証を分ける

1. 事前確認、変更適用、起動後確認を別々に実行できる構造にする。check-onlyは変更しない。dry-runが保証する範囲と、権限や実行時依存で確認できない範囲を分ける。必要条件が未確認なら、それに依存する変更へ進まない。
2. ホスト準備、アプリ配置、永続データを分ける。適用前に変更対象、既存状態の保全方法、途中失敗時の残存物、戻せる範囲を具体化する。既存の承認を使い、未承認の公開・権限拡大・破壊操作が必要な場合だけ、その具体的な変更の直前に確認する。SSHの疎通確認をOS導入や再起動の許可と扱わない。
3. 配布物と設定の検証後、承認範囲の変更を適用する。Composeを使う場合は[compose.md](references/compose.md)を読む。`.sh`を作る場合も、全処理をrootで動かす必要があるとは考えない。
4. 起動・healthに加え、実際のサービスユーザー／コンテナの実行権限で期待するデータが読めること、範囲外を参照できないこと、原本へ書けないこと、専用保存先へ保存できることを、アプリの契約に応じて確認する。rootの成功で代用しない。書込み拒否や保存の試験には合意したテスト用データを使い、原本に試験書込みしない。
5. 更新では旧配布物とデータの互換性を確認する。旧イメージへ戻すこととDB／ファイルを復元することを分ける。復元試験は別の保存先で行い、既存データを上書きしない。

## 失敗を調査・再実行につなぐ

- 各段階の開始・成功・失敗を識別できるようにする。失敗した確認の識別子、終了コード、秘密を除いた理由、変更済み／未実施／不明の状態、次の調査コマンド、再実行条件を残す。
- shellでは`set -e`だけを診断に使わない。重要な確認の終了値を明示的に扱い、必要なら`ERR` trapと`pipefail`を組み合わせる。生のコマンドや`set -x`によるsecret漏えいを避け、trapやログ出力で元の終了コードを失わない。
- SSH切断時は成功・失敗のどちらとも決めず、再接続してプロセス・設定・データの状態を確認する。同じ失敗を状態確認なしに再実行しない。原因や安全な再実行条件が分からなければ依存する適用を止め、読取診断を続ける。
- 復旧は今回変更した範囲に限定する。サービスやvolumeの一括削除を既定のやり直し手段にしない。データ変更の逆操作を機械的に推測しない。

## 検証と引継ぎ

手順／インストーラーを作成・変更したら、適用前に検証条件を決め、限定したテスト環境で正常系・途中失敗・再実行を試す。共有未接続、権限不足、更新失敗、別保存先への復元は関係するケースで含める。本番で障害注入しない。

成果は、配置したバージョン、実測した前提、適用差分、データアクセスの検証、失敗時の記録、再実行／復元手順、未検証範囲を短くまとめる。環境固有情報は利用者管理の領域に残し、公開Issueへ自動転載しない。構文検証、模擬応答、実環境検証を区別し、Piでの成功をUbuntuや別CPUの検証済みにしない。

初期の検証対象はRaspberry Pi OS arm64とUbuntu Server 26.04。全Linux対応、高可用性構築、管理GUIの導入を完了条件に追加しない。
