# Video Game Design

試用版。基本検証と模擬依頼を確認済みだが、実制作での有用性は検証中。試用では設計を実際の試作へ渡せるか、観察から改善を選べるかを確認する。

「プレイヤーが何をして、何を感じ、何を学ぶか」を、試して判断できる遊びへ変える。人物の名声で案を正当化せず、宮本茂を軸とする操作・試行錯誤・観察の視点を、利用者が選んだ体験に合わせて使う。

## 進め方

1. 対象プレイヤー、届けたい体験、入力機器、遊ぶ人数、制作できる規模を既存情報から確認する。判断が変わる不足だけを聞く。ジャンルや2D／3Dを初心者という理由だけで置換しない。
2. 核を「プレイヤーは○○して、△△の手応えを得る」と一文にする。操作と反応、選択と結果から、再挑戦・継続・振り返りなど体験に合う流れを具体化する。勝敗のない創作・探索なら、その流れを無理に勝利条件へ変えない。
3. [creator-lenses.md](references/creator-lenses.md)から今回の課題に関係する観点だけを読む。宮本の観点を出発点に、補助観点を選ぶ。全員の意見を毎回並べたり、本人になりきって助言を創作したりしない。資料の追加や人物への帰属を行うときは[evidence-policy.md](references/evidence-policy.md)を使う。
4. 最も不確かな面白さを一つ選び、最小の試作と観察方法を決める。操作の手応えなら動く試作、選択やルールなら紙の試作も候補にする。仮素材を使い、検証に不要な物語・機能・ステージ数を増やさない。
5. 最初の行動を始める手掛かり、操作への反応、失敗から戻る経路、上達・発見の余地を設計する。「説明しない」は観察条件の一つであり、必要な支援やアクセシビリティまで排除する理由にしない。
6. [playtest-and-handoff.md](references/playtest-and-handoff.md)を使い、試す前に見たい行動と判断条件を置く。観察事実と解釈を分け、採用・変更・保留・削除を決める。実際に遊んだ人の記録がなければ、面白さは未検証と報告する。

## 子ども・家族が対象のとき

[family-play.md](references/family-play.md)を読む。読字、操作経験、役割差、再挑戦、途中退出を扱う。年齢や家族構成を推測して固定せず、子ども向けというだけで競争・難しさ・3Dを排除しない。

## 成果物と境界

短い相談なら、一文の核、変更案、次に試すことを返す。実装へ渡す場合は、操作・ルール・状態遷移・反応・観察条件をまとめる。未確定案を確定仕様として渡さない。

- Unityで作る段階は`unity-beginner-development`へつなぐ。設計だけを頼まれたら、エンジン導入やコード変更は始めない。
- ソフトウェア構造は`technical-design`、開発順序は`implementation-plan`が利用可能ならつなぐ。未導入なら必要な構造・順序だけ直接整理できる。小さなゲームに全工程の文書を必須化しない。
- 実装テストの成功と、プレイヤーが楽しめたという判断を分ける。AIによる机上レビューを人間のプレイテストと呼ばない。
