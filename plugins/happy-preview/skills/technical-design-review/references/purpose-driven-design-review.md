# レビュー観点と記録例

複数の要件・境界、業務上の契約、互換性や安全性が論点になる場合に使う。全項目の記入を求める合否表ではない。対象に関係する経路を選び、証拠と具体的な反例で判断する。

## 目的・要件と実現手段

目的は実現したい状態・価値、要件はその達成に必要な条件、ACは条件の成立を外から確認する方法。レビューはこれらを再決定せず、合意記録へ接続する。

| 合意済み目的・要件と出典 | モデル責任・不変条件（必要時） | 技術上の手段・保証責任 | AC・観測境界 |
| --- | --- | --- | --- |
| [出典の節または既存ID] | [業務条件と適用範囲] | [module / interface / 判断] | [入力・操作・期待結果] |

要件の実現漏れだけでなく、各構造判断に目的・制約・外部contract・安全invariantの根拠があるかも調べる。一つの目的を複数moduleで担うことは問題ではなく、境界間で保証責任が消えることが問題となる。

## 変更容易性と費用

- 何が、なぜ変わるか。合意済みの変更か、根拠のある仮説か。
- どこを変えればよい設計か。実際の依存方向はその範囲に閉じるか。
- 無関係な目的の同時変更や修正漏れが起きる具体的な経路があるか。
- 現在の弊害、変更頻度・影響、改善費用に対して、分割や抽象化が有効か。

たとえば表示用の列追加が更新時の業務条件を変えてしまう設計なら、参照と更新の責務を調べる。一方、データ粒度・完全性条件・利用経路が同じ単純CRUDでは、同じ形を使う判断を許容する。DTO、永続化モデル、ドメインモデルという名前だけで分割を要求しない。

将来シナリオの材料がなければ未確認と記す。変更頻度や将来要件を創作して汎用化を求めない。原則違反の名前を挙げる代わりに、変更時の具体的な影響を説明する。

## モデルと操作の契約

不変条件の意味はdomain modelまたは同等の合意記録、保証手段はtechnical designを正本として扱う。

| 観点 | 確認すること |
| --- | --- |
| 不変条件 | どの対象の、どの状態・期間で成立するか。生成・更新・復元が保証を迂回しないか |
| 事前条件 | 入力・状態を誰が検査するか。UI以外の呼出経路や外部入力でも守れるか |
| 事後条件 | 成功後の状態・戻り値と、合意済み要件の対応 |
| 失敗時 | 拒否・例外・部分成功で残る状態と副作用を説明できるか |
| 並行・再試行（該当時） | 同時更新、重複要求、timeoutで結果が不明な場合にも保証が成立するか |
| 観測 | 正常・境界・拒否例を、公開操作や外部から見える状態で検証できるか |

外部への副作用を戻せないのに、ローカルtransactionだけで「失敗時はすべて元通り」とする保証は成立しない。並行処理では一件ずつの入力検査で満たせても、検査と更新の間に不変条件を破れる場合がある。

反例は、合意済みの条件と実際の設計を使って論理的に示せればよい。実装前のため障害の実測は必須ではないが、将来起こり得る問題を発生済みとは書かない。新しい上限値・権限・許可状態をレビュー側で決めない。

## 技術境界

変更が関係する観点だけを追う。

- module責務、public interface、依存方向、state / data flow、I/Oと所有境界
- 外部入力、認証・認可、secret、file / network / commandのtrust boundary
- API・schema・file formatの互換性、旧利用者と新旧版の共存
- migration、rollback、障害時の復旧と観測。戻せない操作の範囲と代替の回復手段

採用した境界が要件をどう保証するかまで追い、技術名が書かれているだけで十分としない。実装順の詳細、first test、RED/GREEN commandの計画は後工程の担当となる。

## 指摘と記録

重大度は影響と発生条件で説明する。`CRITICAL` は安全・権限・不可逆なデータ損失等の重大な破綻、`MAJOR` は要件・契約や変更時の保証を満たさない問題、`MINOR` は実装を止めない限定的な問題を目安とする。CRITICAL / MAJORが残ればPASS系にはしない。単なる確認質問や好みを指摘数に含めない。

```markdown
### [MAJOR] 同時引受で担当が二人へ確定する

- Evidence: 合意記録 R-01、設計 D-02「未割当を読む→担当を保存」
- Affected purpose / requirement: 二重対応を防ぐ / R-01
- Condition / harm: 二要求が更新前の未割当を読むと双方が成功を返せる。
  最後の保存だけが残っても、二人が担当確定を通知され二重対応を始める。
- Smallest correction: 引受確定を一人に限定する保証を保存境界に置き、競合時の結果を契約へ記載する。
- Return path: technical-design（業務要件は合意済み）
```

推奨する保存項目：

```markdown
# Technical Design Review NNN: [Name]

## Verdict / Review Scope
## Reviewed Revision / Reviewer Independence
## Normative Sources / Assumptions / Unknowns
## Traceability Assessment
## Findings
## Accepted Conditions / Residual Risks
## Return Path / Re-review Scope
```

項目は統合できる。条件付きPASSでは、条件、実装を止めない理由、受容した所有者と出典、担当、確認時点を追えるようにする。記録のない受容を補わない。再レビューでは旧recordへの参照、対象の新版、指摘の解消と新たな影響を残す。
